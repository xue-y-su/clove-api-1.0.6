## 3. 总体诊断

这些问题不是同一个 500 的不同表现，而是五类缺陷叠加：

1. **查询路径错误：** 已有聚合表，但用户关联查询仍扫描约 84 万条原始 IP 事件，导致页面慢、明细截断和汇总口径混乱。
2. **部署拓扑未纳入业务键：** 可信代理只配置了回环地址，Docker 网关被当作真实客户端 IP；共享临界限流桶进一步把不同用户的行为合并。
3. **类型边界错误：** 钱包长期余额和兑换码额度复用了单次请求计费的 `int32` 饱和边界，大额合法余额被错误拒绝。
4. **前后端契约分叉：** 后端已经支持按分组查询模型，前端却不传分组；Default 对可缺省联网搜索来源直接 `.map()`，Classic 又采取另一套容错。
5. **状态机与认证时序不完整：** 公告在登录态恢复前按游客流程执行，邀请码拒绝态不随冷却结束退出，自动 API Key 与自定义 API Key 共用不适合的生成语义。

修复必须按“数据口径和安全边界优先、阻断 500 次之、交互和翻译收口最后”的顺序实施。只改页面文案或增加 loading 不会解决根因。

## 4. 安全与 IP 审计

### 4.1 已确认问题

#### 4.1.1 用户详情查询扫描原始事件

**[已复现]** `service/ip_security_user_projection.go:223-245` 为查找关联用户直接扫描 `ip_security_events`。当前数据量约为：

- 原始事件：`840,064` 条。
- 同类关系查询耗时：约 `8.3s`。
- 已存在的 `IPAuditRollup`：约 `11,777` 条。
- 基于 rollup 的同类查询耗时：约 `21ms`。
- 用户 `#1` 当前关联约 `1,240` 个 IP、`403` 个历史身份。

根因不是前端渲染慢，而是列表接口选择了错误的数据层。`model/ip_security_event.go:62-80` 已经存在可承担关系查询的聚合模型，却没有用于该路径。

#### 4.1.2 汇总数量与明细天然不一致

**[源码确定]** 当前关联用户列表硬限制为 50 条，IP 详情硬限制为 20 条，但页面仍展示未截断总数。用户看到“300 个账号共用”却只能看到少量账号，不是偶发漏数据，而是 API 契约没有表达 `total`、`returned`、`has_more` 和分页游标。

#### 4.1.3 共享调用 IP 被误读为共享注册 IP

**[已复现]** 当前共享 IP 前五名关联账号数为 `300 / 231 / 230 / 179 / 126`，对应注册次数均为 0。它们来自 API 调用事件，不是 300 人从同一个地址注册。

注册 IP 覆盖率仅为 `7 / 2852`，其中 5 条是私网地址。当前页面把 API 调用、登录、注册和管理行为堆在同一组数字中，导致一个真实的“共享调用出口”被解释成更严重但并不存在证据的“批量同 IP 注册”。

#### 4.1.4 Docker 网关污染真实客户端 IP

**[环境配置]** 当前容器观测到：

```text
TRUSTED_PROXIES=127.0.0.1
Docker gateway=172.17.0.1
```

`172.17.0.1` 没有被声明为可信代理，因此代理后的请求会把 Docker 网关写成客户端 IP。该地址当前聚合了 17 个账号、93 次成功登录和约 410 个事件。它不能作为账号关联风险证据。

#### 4.1.5 风险分类和事件语义不足

**[源码确定]** 当前页面缺少独立的“风险、共享调用 IP、共享注册 IP、登录异常、单用户轨迹”视图，异常项也没有稳定置顶。`activity_3` 等活动最终显示为“其他活动”，说明事件模型或转换链没有保留足够的业务 `action`。

IPv6 文本没有稳定的断行和列宽约束，长地址会压住相邻字段。这个是展示缺陷，但不是慢查询根因。

### 4.2 目标数据模型

IP 审计应明确分为三种事实，禁止再用一个“关联用户”概念概括：

| 事实类型 | 账号语义 | 主要用途 |
| --- | --- | --- |
| 注册事实 | 创建账号的用户 | 同 IP 批量注册、邀请滥用 |
| 认证事实 | 直接执行登录、登出、OAuth、解绑的用户 | 异地登录、暴力尝试、账号接管 |
| API 调用事实 | 被使用 API Key 的所有者 | Key 共享、代理出口、异常地域调用 |

原始事件表继续作为可追溯事实源；`IPAuditRollup` 作为列表、排序、风险摘要和关系查询的唯一在线读取源。只有用户打开某个 IP 或某个账号的具体时间线时，才分页读取原始事件。

聚合键至少包含：

```text
normalized_ip + subject_user_id + event_family + time_bucket
```

其中 `event_family` 必须是 `registration`、`authentication`、`api_call` 或 `administrative` 等稳定枚举，不能从任意英文 `content` 临时猜测。

### 4.3 查询与 API 修复方向

1. 用户页摘要只查询 rollup，不扫描原始事件。
2. IP 列表按风险分数、最后活动时间和事件数建立可解释排序；默认“有问题的在前”。
3. 共享调用账号、共享注册账号分别计数，任何接口都不得把两者相加后显示为同一指标。
4. 每个明细接口返回 `items`、`total`、`page_size`、`next_cursor` 或等价分页字段。
5. 大列表使用稳定游标分页，避免在持续写入时使用大偏移量造成重复和漏项。
6. 原始事件读取必须带时间范围、事件类型和主体过滤，禁止无条件全表扫描。
7. “相关账号”详情明确标注关系来源：`API Key 所有者`、`登录账号`、`注册账号`。
8. `activity_n` 在写入时归一化为稳定 action；历史未知值显示“未知活动（原始值：activity_n）”，不得伪装成明确业务结论。

### 4.4 页面信息架构

独立安全与 IP 审计页面保留，并拆成以下视图：

1. **风险总览：** 高风险共享注册、异常登录、短期跨地域、同 Key 多出口等可行动项目，默认按严重度降序。
2. **共享调用 IP：** 强调可能是公司出口、代理或共享 Key，不自动定性为注册作弊。
3. **共享注册 IP：** 只使用真实注册事实；数据覆盖不足时明确展示覆盖率。
4. **登录异常：** 成功、失败、OAuth 和安全操作分开过滤。
5. **IP 查询：** 输入 IPv4/IPv6 查看账号和事件时间线。
6. **用户查询：** 输入用户 ID 查看注册 IP、登录 IP、调用 IP，默认只加载摘要。

IP 字段使用等宽字体、复制按钮、`overflow-wrap:anywhere` 和稳定列宽。IPv6 可换行但不能与风险徽标、账号数或操作列重叠。

### 4.5 可信代理修复

可信代理不是仅改一个默认值。实施时必须：

1. 从实际反向代理拓扑列出允许注入 `X-Forwarded-For` 的网段。
2. 容器直连部署加入实际 Docker 网关或代理容器网段；不允许信任 `0.0.0.0/0`。
3. 启动时记录“有效可信代理列表”，但不记录密钥或请求正文。
4. 检测到高比例请求集中在私网网关时产生部署告警，提示审计数据可能失真。
5. 配置修复后的新数据与旧污染数据分层：旧网关 IP 保留原始事实，但从风险判定中标为 `proxy_artifact`，不得静默删除。

### 4.6 性能和正确性验收

- 100 万原始事件规模下，用户 IP 摘要接口本地 p95 小于 300ms。
- rollup 主查询应稳定小于 100ms；任何摘要接口不得出现原始事件全表扫描。
- 首屏只加载一页摘要，不因 1,240 个 IP 或 403 个身份阻塞整个页面。
- 页面总数与分页元数据一致，用户可以继续加载全部 300 个关联账号。
- 共享注册指标只来自注册事实；注册覆盖率始终可见。
- Docker 网关和受信代理地址不会作为真实共享客户端风险告警。

## 5. 异常限流

### 5.1 已确认根因

**[源码确定]** `middleware/rate-limit.go:40` 使用 `rateLimit:<mark><ClientIP>` 作为键。`CriticalRateLimit` 在 `middleware/rate-limit.go:160-164` 统一使用 `CT` 标记，默认限制是 20 次 / 20 分钟（`common/constants.go:233-235`）。

`router/api-router.go` 约 53 个敏感路由共用同一个 `CT + IP` 桶。登录、资料修改、头像、邀请码、钱包、支付和管理员操作会互相消耗额度。再叠加错误的可信代理配置，不同真实用户可能共享同一个 Docker 网关键，因此出现“没有频繁操作也被限流”。

### 5.2 修复设计

限流键改为“策略 ID + 主体 + 必要的网络维度”，不同业务不可共享一个匿名 `CT` 桶：

| 策略 | 主体 | 目的 |
| --- | --- | --- |
| `auth.login.ip` | 规范化客户端 IP | 限制同源暴力登录 |
| `auth.login.identity` | 用户名/邮箱的不可逆摘要 | 防止攻击者轮换 IP |
| `auth.register.ip` | 规范化客户端 IP | 限制批量注册 |
| `profile.write.user` | 已登录用户 ID | 限制资料、头像更新，不受其他用户影响 |
| `invitation.write.user` | 已登录用户 ID | 邀请码申请、撤回和校验分开计数 |
| `wallet.write.user` | 已登录用户 ID | 钱包和兑换码写操作独立计数 |
| `payment.write.user` | 已登录用户 ID | 支付创建与回调管理分离 |
| `admin.write.user` | 管理员用户 ID | 管理操作不与普通用户登录共享 |

登录等未认证接口同时使用 IP 与身份摘要两个桶；已认证写操作以用户 ID 为主、IP 为异常补充信号。不能仅改成用户 ID，否则失去登录前防护；也不能继续仅按 IP，否则公司网络、移动出口和反向代理下会误伤。

所有 429 响应统一返回：

```json
{
  "success": false,
  "code": "RATE_LIMITED",
  "message": "操作过于频繁，请在 42 秒后重试",
  "retry_after": 42,
  "request_id": "..."
}
```

并设置标准 `Retry-After` 响应头。前端不得只显示“请求失败”或原始英文错误。

### 5.3 验收标准

- 连续编辑资料不会消耗登录、邀请码或钱包的额度。
- 两个用户从同一受信代理访问时，已认证写操作互不占用主限流桶。
- 同一账号轮换 IP 暴力登录仍被身份桶拦截。
- 限流日志包含策略 ID、主体类型和重试秒数，不记录明文密码、完整 API Key 或邮箱摘要原文。

## 6. 游乐场

### 6.1 分组与模型不一致

**[源码确定]** 后端 `controller/user.go:767-821` 已支持按 `group` 查询模型；不传 `group` 时会合并用户所有可用分组。

两套前端都没有正确传分组：

- Default：`web/default/src/features/playground/api.ts:78-80` 的 `getUserImageModels()` 不接收分组；`playground-image-panel.tsx:123-145` 只在首次加载模型。
- Classic：`web/classic/src/components/playground/PlaygroundImagePanel.jsx:102-145` 直接请求 `/api/user/models`，同样不传分组。
- 现有测试还明确断言“不传 group”，因此测试锁死了错误行为，而不是保护正确契约。

修复后，选定分组是模型查询键的一部分：

```text
queryKey = ["playground-image-models", selectedGroup]
GET /api/user/models?group=<selectedGroup>
```

切换分组时取消旧请求、清空不属于新分组的旧模型选择、重新加载并自动选择新列表中的第一个合法模型。模型选择器增加本地搜索；空结果显示“该分组没有可用模型”，不能回退展示其他分组。

### 6.2 联网搜索整页 500

**[源码确定]** Default 的 `web/default/src/features/playground/hooks/use-chat-handler.ts:168-175` 对可缺省的 `update.metadata.sources` 直接执行 `.map()`。当上游没有返回来源数组时会抛出前端运行时异常，导致页面错误边界显示 500。

Classic 已使用 `metadata.sources || []`，两套行为不一致。修复应在协议归一化层把缺失、`null` 和非法来源统一为 `[]`，组件只消费归一化结果。不能在每个渲染点零散加可选链。

### 6.3 图片参数与 503

**[源码确定]** “输出 URL”是协议响应格式，不是用户可调参数，页面不应把它渲染成设置。质量和背景只有同时满足以下条件时才显示：

1. 请求构造器确实发送对应字段。
2. 当前渠道/模型能力声明允许该字段。
3. `rightcode` 实际验证接受非默认值。

**[尚未复现]** `Request failed with status code 503` 目前不能归因到前端。实施时必须保存同一请求 ID 下的三段证据：CloveAPI 入站请求、发往 `rightcode` 的归一化参数、上游状态和响应摘要。之后才能区分上游不可用、渠道调度失败、参数拒绝和响应解析错误。

503 不能通过隐藏错误或自动无限重试处理。只对明确幂等、没有收到上游业务响应的瞬时错误做有限退避，且保留请求 ID。

### 6.4 验收标准

- 选择 `Select` 后只出现 `Select` 可用模型，切换到其他分组后列表立即同步。
- 搜索模型不会改变后端分组过滤，也不会让已失效模型继续提交。
- 联网搜索响应没有 `sources` 时仍能完成对话，不触发页面级 500。
- 页面不显示假的“输出 URL”控件。
- 每个可见质量、背景控件都能在出站请求中找到对应字段，并通过 `rightcode` 实测。

## 7. 邀请码与注册校验

### 7.1 邀请码过长

**[源码确定]** `service/invitation.go:532-538` 生成 18 字节随机值，再使用 Base64URL 并添加 `inv_` 前缀，长度明显超过原 new-api 的短邀请码体验。

新码采用 8 位无前缀 Crockford Base32：

```text
字符集：0123456789ABCDEFGHJKMNPQRSTVWXYZ
示例：7K9M2XQP
```

该字符集排除易混淆的 `I/L/O/U`，8 位提供约 40 bit 空间。数据库唯一约束仍是最终防线，生成器遇到碰撞重试有限次数，超过后返回内部错误并记录请求 ID。

兼容策略：

- 已存在的 `inv_...` 长码继续可用、可撤销、可审计。
- 不批量改写旧码，不让已分享链接失效。
- 新申请和管理员新发放只生成短码。
- 输入比较统一大小写，但数据库保存规范化大写值。

### 7.2 邀请链接和自动填充

**[当前已解决]** 邀请链接构造已存在于 `web/default/src/features/invitation/invitation-state.ts:74-80` 和 `user-invitation-card.tsx:128-132`；注册页 `sign-up-form.tsx:142-145` 已支持 `?aff=` 自动填充。

缺口是用户卡片没有把完整注册链接作为主要可复制信息。修复后同时显示短码和完整链接，各自只有一个明确复制按钮；二维码使用同一链接源，避免三处拼接逻辑分叉。

### 7.3 注册页实时校验

**[源码确定]** 当前没有面向注册页的公开邀请码校验接口，因此前端无法在自动填充后显示可靠的绿色勾或红色叉。

新增公开只读校验必须满足：

- 输入长度、字符集先本地校验。
- 300–500ms 防抖，并取消过时请求。
- 服务端使用独立 `invitation.validate.ip` 限流策略。
- 返回 `valid`、稳定错误码和用户可理解文案，不返回码所有者、剩余次数、审核信息等可枚举隐私。
- 无效、过期、禁用、耗尽对未登录用户可统一为“邀请码不可用”；前端仍可用统一红叉表达。
- 注册提交时再次执行权威校验，实时绿勾不能替代事务内校验。

### 7.4 拒绝冷却状态

**[源码确定]** 后端已有 `can_apply` 和 `reapply_at`，但前端主要根据最后记录的 `rejected` 渲染红色状态。冷却结束后底部虽然可再次申请，旧红色拒绝主提示仍保留。

状态机必须以服务端 `can_apply` 为最终依据：

- `rejected && !can_apply`：显示拒绝原因和可再次申请时间。
- `rejected && can_apply`：回到普通申请态，历史拒绝只留在记录列表。
- `pending`：显示审核中和允许的撤回操作。
- 已有活动邀请码：显示短码、链接、类型、使用量和到期时间。

邀请奖励区域按内容自身高度布局，不与长状态卡等高拉伸。

### 7.5 验收标准

- 新码固定 8 位、无 `inv_` 前缀；旧长码继续注册成功。
- `?aff=<code>` 自动填充后自动校验，可用显示绿色勾，不可用显示红色叉和明确文案。
- 冷却结束后不再显示过期红色主提示，但管理员仍能看到拒绝历史。
- 码、链接、二维码来自同一个规范化链接生成函数，复制按钮各只有一个且可用。

## 8. 用户兑换码与钱包额度

### 8.1 已确认根因

**[源码确定]** `controller/user_redemption.go:14-20,91-103` 使用 `int` / `float64` 接收额度；`common/quota_math.go:15-17` 将 `MaxQuota` 固定为 `math.MaxInt32`。控制器把标准金额转为 quota 后，`service/user_redemption.go:242-259` 再按同一 `MaxQuota` 拒绝。

当标准单位对应 `500,000 quota` 时，合法金额大约超过 `4294.97` 就会触发 `wallet adjustment is invalid`。这不是用户余额不足，也不是兑换码业务规则，而是把“单次模型请求计费上限”误用成“长期钱包余额和兑换码额度上限”。

数据库中的钱包相关列已经是 BIGINT，但以下模型仍大量使用 `int` 或 `gorm:"type:int"`：

- `model/user.go:62-69`
- `model/user_redemption.go:24-27`
- `model/wallet_ledger.go:8-9`

Go 的 `int` 在当前 64 位环境可能暂时容纳更大值，但类型、GORM 标签和通用 quota 转换仍会提前按 int32 拒绝，形成跨层不一致。

### 8.2 类型边界设计

后续明确拆分两种量：

1. **单次计费 quota：** 继续受现有 `common.QuotaFrom*Checked` 和 int32 饱和保护，防止单个模型请求溢出或产生负扣费。
2. **钱包持久金额：** 使用显式 `int64` 类型，覆盖用户余额、冻结额、兑换码额度、钱包流水 delta 和 balance_after。

禁止通过放大 `common.MaxQuota` 解决问题。那会同时削弱单次计费安全边界。钱包转换应新增独立、可审计的 decimal-to-int64 路径：拒绝 NaN、Inf、负数、超精度和 int64 溢出，并返回字段级错误。

HTTP 输入不再依赖二进制 `float64` 表示金额。新契约优先接受十进制定点字符串；兼容旧数值 JSON，但统一解析为 decimal 后再转换。响应同时返回标准金额字符串和 quota 整数，避免前端再次自行乘除导致 `0.00几` 的单位错误。

### 8.3 数据库迁移顺序

迁移必须保持三数据库和旧版本回滚能力：

1. **迁移前审计：** 记录相关列类型、最大最小值、负数异常、兑换码与 ledger 对账差异；先做数据库备份。
2. **先宽化数据库：** MySQL 使用 BIGINT，PostgreSQL 使用 BIGINT，SQLite 的 INTEGER 本身为 64 位但需移除会诱导错误迁移的 `type:int` 标签。
3. **再发布 int64 模型：** Controller、Service、Model、DTO 和缓存结构一次完成类型贯通，禁止中间层转回 `int`。
4. **再切换钱包转换器：** 只有钱包和兑换码路径使用新 int64 转换；模型请求计费继续使用原有 checked quota helper。
5. **校验与回填：** 比较用户余额、有效兑换码总额、ledger 末笔余额和退款引用；不自动改写无法解释的历史差异。

数据库宽化对旧二进制是向后兼容的，因此回滚应用时保留 BIGINT，不执行危险的窄化回滚。SQLite 如需重建表，必须采用建新表、复制、校验行数、原子替换的项目既有迁移模式。

### 8.4 业务校验与错误信息

创建兑换码时依次校验：

1. 金额存在且是正数。
2. 小数精度符合系统标准单位。
3. 转换后的 quota 不溢出 int64。
4. 用户可用钱包余额足够。
5. 单码和批量总额符合余额与管理员策略。

失败响应必须定位字段，例如：

```json
{
  "success": false,
  "code": "REDEMPTION_AMOUNT_EXCEEDS_BALANCE",
  "field": "amount",
  "message": "兑换码额度 5000.00 超过当前可用余额 4382.75",
  "request_id": "..."
}
```

不得再用没有上下文的 `wallet adjustment is invalid` 覆盖所有失败原因。

### 8.5 钱包审计日志

内部 wallet ledger 必须保留，它承担幂等、退款、对账和管理员审计，不能因用户不需要“钱包流水页面”而删除。用户侧统一在使用日志展示业务化描述：

```text
创建用户兑换码 RC-XXXX：扣除 5000.00，余额 9382.75 -> 4382.75
管理员撤销兑换码并退款：退回 1200.00，余额 4382.75 -> 5582.75
```

结构字段至少包含 `category`、`reason`、`delta`、`balance_before`、`balance_after`、`reference_type`、`reference_id`、`operator_id` 和 `request_id`。敏感兑换码只展示脱敏引用。

### 8.6 验收标准

- 创建 5,000、50,000 等余额允许范围内的兑换码不再触发 int32 上限。
- 超余额、负数、过多小数、超 int64 范围分别得到不同且可理解的错误。
- 创建、领取、禁用、删除和管理员决定退款/不退款后余额、兑换码和 ledger 三方一致。
- SQLite、MySQL、PostgreSQL 执行同一用例得到一致金额和错误码。
- 单次模型请求的 int32 计费饱和保护保持不变。

## 11. 全局公告与认证时序

### 11.1 已确认根因

**[源码确定]** `router/api-router.go:55` 使用 `TryUserAuth()` 暴露公告状态，游客也可请求。Default 在 `web/default/src/routes/__root.tsx:54` 全局挂载公告弹窗，查询不依赖登录 hydration 完成；Classic 的 `PageLayout.jsx:233` 和 `GlobalAnnouncementModal.jsx:55-105` 也允许游客流程。

认证状态恢复时，页面可能先以游客身份读取 localStorage，随后变成登录用户并调用服务端确认。与此同时 Default 的合规声明和来源归属 gate 在 `authenticated-layout.tsx:48-49` 并行挂载，而公告位于更外层根布局。新用户因此可能同时遇到多个阻塞弹窗，并在身份切换后出现“公告确认失败”。

### 11.2 正确流程

未登录用户不请求、不展示、不确认全局公告。登录后的阻塞流程必须串行：

```text
认证 hydration 完成
  -> 合规声明
  -> 来源归属
  -> 最新未确认公告
  -> 正常页面
```

每个 gate 只有三种结果：`loading`、`required`、`satisfied`。后一个 gate 只有在前一个 `satisfied` 后才发请求。公告确认失败时保留弹窗和内容，显示可重试错误，不得先关闭再报错。

服务端公告状态与确认接口改为强制登录鉴权。若仍需要公开公告列表，应与“登录后弹窗确认”使用不同路由和 DTO，不能复用一个 `TryUserAuth` 接口形成双重身份语义。

### 11.3 服务器图片

**[当前已解决]** 当前源码已存在管理员服务器图片上传和持久化实现，不应重新改回外部图床 URL。后续只验证：

- 管理端正方形加号上传交互。
- 文件类型、大小、像素、哈希命名和同源读取。
- Docker 持久卷重建后图片仍存在。
- 公告删除或替换后的受管文件清理不会误删当前引用。

### 11.4 验收标准

- 未登录打开站点不发公告状态或确认请求，也不弹公告。
- 新注册用户只按既定顺序看到一个阻塞弹窗。
- 换浏览器登录同一账号后，已确认公告不重复弹出。
- 确认网络失败时弹窗不消失，可重试且不会与合规声明冲突。

## 12. 自动与自定义 API Key

### 12.1 已确认现状

**[源码确定]** `common/utils.go:261-264` 的 `GenerateKey()` 只返回 48 位随机字符串，没有 `sk-`。自动 Key 创建位于 `controller/token.go:414-424`，注册默认 Key 位于 `controller/user.go:365`，两者因此都缺少期望的自动前缀。

**[当前已解决]** 自定义 Key 的校验和碰撞处理已经存在：

- 校验：`controller/token.go:66-89`
- 碰撞禁用与审计：`controller/token.go:111-168`

需求不是给所有 Key 强制添加前缀，而是：

- 自动生成：`sk-` + 随机主体。
- 用户自定义：原样保存，不增删 `sk-`。
- 历史无前缀 Key：继续认证，不做批量改写。

### 12.2 修复设计

不要改变泛化 `GenerateKey()` 的全局语义。新增显式 API Key 生成函数，例如 `GenerateAPIKey()`，只在自动创建 token 和注册默认 token 时调用。自定义路径绕过该生成器，继续执行长度、字符集、唯一性和碰撞处置。

认证不按前缀分支，仍按完整 Key 查找，因此旧 Key、自动新 Key和自定义 Key可以并存。列表通过独立 `key_origin` 或可靠元数据区分 `generated/custom`，不能根据字符串是否以 `sk-` 开头猜测，因为用户自定义值也可能自行包含该前缀。

### 12.3 验收标准

- 自动创建和注册默认 Key 都以 `sk-` 开头。
- 自定义 `abc_xyz-123` 保存后仍为原值，不被加前缀。
- 自定义 `sk-my-own-key` 也保持原值。
- 旧无前缀 Key 继续调用成功。
- 自定义 Key 碰撞仍禁用旧 Key、审计且不泄露旧所有者。

| 联网来源 | 都把缺失 sources 归一化为 `[]` |
| 邀请码 | 同一短码、链接、实时校验和冷却状态机 |
| 日志 | 覆盖同一 action 集合，中文语义一致 |
| Profile | 同一三个元信息和昵称冷却规则 |
| 公告 | 都只在登录完成后进入串行 gate |
| API Key | 同一自动前缀、自定义原样和碰撞规则 |
| 错误反馈 | 都优先显示结构化 `code/message/field/request_id` |

可以共享纯数据契约、action 清单和测试样例；不要为了共享 UI 而强行跨 React 版本抽组件。

## 15. 统一错误契约与可观测性

所有本轮相关 API 失败采用稳定结构：

```json
{
  "success": false,
  "code": "STABLE_MACHINE_CODE",
  "message": "面向当前语言用户的可执行说明",
  "field": "optional_field_name",
  "retry_after": 0,
  "request_id": "correlation-id"
}
```

实施时新增或核对以下观测指标：

- IP 摘要和详情查询耗时、扫描行数、rollup 延迟。
- 按策略 ID 统计的限流拒绝数和主体类型。
- 游乐场上游状态、渠道、模型、参数类别和请求 ID；不记录提示词全文。
- 邀请码校验结果聚合，不记录完整码。
- 钱包调整的业务类别、delta、前后余额和引用。
- 头像上传阶段、错误类别和目标主机，不记录临时签名参数。
- 公告 gate 阶段、确认失败码和认证 hydration 状态。

页面级错误边界只处理真正不可恢复的渲染异常。业务 4xx、上游 503、空数组和超时不得把整个页面替换成 500。

## 17. 测试矩阵

本节规定后续实施的验证范围；本轮没有执行这些测试。

### 17.1 后端

- IP rollup：100 万事件夹具、共享调用与共享注册分离、分页完整性、代理污染标记。
- 限流：各策略桶互不影响、登录双维度、Redis 与内存实现一致、`Retry-After` 正确。
- 邀请码：短码碰撞重试、旧长码兼容、过期/禁用/耗尽、并发领取、公开校验防枚举。
- 钱包：正数、精度、边界、溢出、并发创建、禁用、删除、管理员退款/不退款、幂等重试。
- 公告：未登录拒绝确认、gate 顺序、签名幂等、图片持久化。
- API Key：自动前缀、自定义原样、碰撞、旧 Key 认证。
- Profile：昵称冷却、只改头像、无变化提交、字段错误和会话保持。

### 17.2 数据库

同一测试套件在以下环境运行：

- SQLite 当前支持版本。
- MySQL 5.7.8 及目标生产版本。
- PostgreSQL 9.6 及目标生产版本。

重点检查 BIGINT 迁移、唯一约束、事务锁、并发余额调整、邀请码碰撞和公告确认幂等。SQLite 不使用不支持的 `ALTER COLUMN` 或 `FOR UPDATE`。

### 17.3 前端

- Default 与 Classic 都覆盖分组切换、模型搜索、缺失 sources、邀请码校验、冷却结束、公告 gate、Profile 冷却和结构化错误。
- action 清单契约测试阻止后端新增日志动作后某一套前端漏翻译。
- 桌面和移动宽度检查 IPv6、状态徽标、邀请奖励卡和 Profile 元信息不重叠。

### 17.4 浏览器角色

| 角色 | 核心流程 |
| --- | --- |
| 未登录 | 注册链接自动填码、实时校验、不请求公告 |
| 新用户 | 注册、合规、来源归属、公告串行确认 |
| 普通用户 | 游乐场、资料、头像、邀请码、兑换码、日志 |
| 管理员 | 用户兑换码全量治理、日志详情、公告发布、安全审计 |
| Root | 系统设置、来源归属旧配置迁移、IP 策略和全局审计 |

### 17.5 上游与故障注入

- 使用本地模拟网关分别返回 200、400、401、429、503、超时、断流和畸形 JSON。
- 对 `rightcode` 真实验证基础生图、质量、背景和模型分组。
- 确认所有失败只影响当前操作，不触发页面级 500，不丢失用户输入。

## 18. 发布、回滚与数据安全

1. 发布前备份主数据库、日志数据库和公告媒体卷，并记录镜像、提交和迁移版本。
2. 先发布向后兼容的数据库宽化，再发布新应用；不在同一步删除旧列或旧邀请码格式。
3. IP rollup 可由原始事件重建，切换查询前先比较新旧汇总并保存差异报告。
4. 新限流策略使用新键前缀，回滚旧版本时旧 `CT` 键自然恢复，不批量删除 Redis 其他数据。
5. 回滚应用时保留 BIGINT、短邀请码和已写结构化日志；旧应用必须仍能读取这些值，超出旧应用安全范围时阻止旧版本启动并提示，而不是截断。
6. 公告 gate 可通过已有公告弹窗功能开关临时关闭，但不能退回游客确认语义。
7. 生图高级参数可按模型能力关闭；基础游乐场和其他模型调用不随单个渠道故障整体下线。

- 公告在游客和登录 hydration 阶段执行，和合规/来源 gate 竞争。
- 自动 API Key 未添加 `sk-`，自定义路径本身不应添加。

## 20. 旧设计文档的处理

保留 `2026-07-21-seven-area-production-hardening-design.md` 作为历史设计记录，但以下结论以本文件为准：

1. 公告不再允许游客弹窗或游客确认。
2. 自动生成 API Key 应带 `sk-`，自定义 Key 才保持原样。
