**日期：** 2026-07-14
**状态：** 已结合实际代码审查确认，待实施计划
**范围：** 工作区治理、用户资料与权限、邀请码、Token 与钱包、Playground、审计与 IP、用户兑换码、邮件模板、Snow 首页、双前端验收

本文把已经逐项确认的设计合并为唯一实施基线。以下资料继续作为背景和验收证据，但发生冲突时以本文为准：

- `2026-07-13-user-governance-playground-design.md`；
- `2026-07-14-remove-super-root-design.md`；
- `2026-07-14-snow-home-delivery.md`；

特别说明：本文的邀请码申请审批制度替换旧的自动个人邀请码和单纯邀请人数上限制度；自定义 API Key 改为允许所有者多次查看完整值，但每一次查看都必须通过服务端限流并记录敏感读取审计。其他既有功能没有被本文明确替换时继续保留。

不得修改、删除或替换 New API、QuantumNous 相关的受保护标识、归属、模块路径和项目元数据。CloveAPI 功能在现有项目结构内扩展。

## 2. 目标与非目标

### 2.1 目标

1. 清理并分类当前混合工作区，使源码、必要静态资源、测试和本地产物边界清楚。
2. 以数据库、后端、default、classic、测试和浏览器验收组成垂直功能切片，每个切片独立提交、可单独回滚。
3. 补齐用户资料、权限、邀请码、Token、钱包、Playground、审计、兑换码和邮件模板的业务闭环。
4. Snow 只作为根路径首页内容，完整保留 New API 的导航、应用外壳和其他路由。
5. 所有持久化和事务逻辑同时支持 SQLite、MySQL 和 PostgreSQL。

### 2.2 非目标

- 不增加 `super_root` 字段、角色或授权分支。
- 不创建永久图片图库，不持久化 Playground 生成图片二进制或聊天历史。
- 不让浏览器直接访问 Tavily、SMTP 或图片上游凭据。
- 不把订阅剩余额度并入钱包主余额。
- 不用一次性大提交掩盖工作区中的未审查改动。
- 不删除第三方图床中的旧头像；CloveAPI 只保存受信任图片 URL。
- 不重写 default 和 classic 为同一套组件；两者共享契约和行为，不共享 UI 实现。

## 3. 总体交付架构

每个功能切片固定经过以下层次：

1. **数据层：** 表、字段、迁移、索引、状态机、事务和幂等约束。
2. **后端层：** Router -> Controller -> Service -> Model，集中权限校验并写审计。
3. **default 前端：** 使用现有 React 19、Base UI 和 Tailwind 模式完成全部流程。
4. **classic 前端：** 使用现有 React 18 和 Semi Design 模式完成同等流程。
5. **验证层：** 单元/集成测试、构建、桌面和移动浏览器验收、提交检查。

前端只能根据后端能力和权限改善体验，不能承担授权。default 与 classic 必须保持相同的入口、字段语义、权限、状态机、成功/失败结果和关键验收用例，同时保留各自原生视觉风格。

所有用户可见文本、错误消息、状态标签和邮件模板管理界面都必须接入现有 i18n 体系；default 与 classic 各自维护原生组件，但共享英文键语义和验收文案，不在组件中硬编码只支持单语言的产品文本。

所有写操作都要有 pending、成功、页内错误和可重试状态。危险操作要二次确认并说明失效、退款或权限影响。移动端使用单列或卡片布局，不能依赖横向滚动完成关键操作。

## 4. 工作区治理

### 4.1 文件分类

- **必须保留并纳入相应功能提交：** 业务源码、迁移、有效测试、设计文档及运行必需的 `web/snow/dist/**`。
- **保留在本地但忽略：** `.build-cache/**`、`.superpowers/**`、验收数据库、二进制、日志、截图、Playwright 证据和临时报告。
- **只有核对引用和 Git 来源后才能删除：** 重复夹具、过期生成物或已被正式文件替代的临时文件。
- **禁止：** `git reset --hard`、用 checkout 覆盖现有改动、批量暂存整个工作区、提交真实密钥或本地运行数据。

### 4.2 提交规则

- 先建立状态清单，再按功能文件选择性暂存。
- 每个提交只包含一个可描述、可验证的垂直切片。
- 提交前执行 `git diff --check`、敏感信息检查和目标文件清单核对。
- Snow 静态资源是编译依赖，不得因其为生成产物而漏交；本地验收二进制和数据库不得提交。
- 最终源码包只从干净 Git 工作树中的已跟踪文件生成。

## 5. 用户角色、资料与封禁

### 5.1 角色矩阵

系统只保留 User、Admin、Root：

| 操作 | Admin | Root | 用户 ID=1 |
| --- | --- | --- | --- |
| 管理普通用户 | 是 | 是 | 是 |
| 提升普通用户为 Admin | 否 | 是 | 是 |
| 管理 Admin | 否 | 是 | 是 |
| 提升或降级其他 Root | 否 | 否 | 是 |
| 禁用或删除 Root | 否 | 否 | 否 |

- ID=1 不能降级自己。
- 其他 Root 只能管理 User 和 Admin，不能变更 Root 身份。
- 角色、封禁和安全状态变化后，立即失效相关用户、Token、会话和授权缓存。
- 既有数据库中的遗留 `super_root` 列可暂时保留，但运行时不读取、不写入，新数据库不创建该列。

### 5.2 用户名与昵称

- `display_name` 是显示昵称，新账户默认为用户名。
- 普通用户不能修改用户名；可修改昵称和头像。
- 昵称首次设置可以立即保存，之后受系统昵称冷却期约束，默认 7 天。
- 系统设置控制昵称最大长度和冷却天数，服务端始终强制校验。
- 昵称允许正常可见 Unicode，包括中文、英文、数字、emoji 和常用符号；拒绝控制字符、HTML 标签、危险双向控制符和空白滥用。
- Admin/Root 可修改自己的用户名；Admin 可改普通用户用户名，Root 可改普通用户和 Admin 用户名。
- 用户名修改必须做格式、唯一性、角色层级和乐观并发校验，并写审计和失效缓存。
- 若昵称仍与旧用户名相同，管理者修改用户名时可同步昵称；已自定义昵称不得被覆盖。

`GET /api/user/self` 和对应资料类型必须返回 `avatar_url`、`display_name`、用户名以及昵称下次允许修改时间。`UpdateSelf` 必须执行与管理端一致的昵称、头像和冷却校验，不能只依赖前端。

新增 `OwnProfile` 模块处理本人资料读取和修改，集中执行昵称冷却、头像白名单、密码变更和缓存失效；不能继续把安全规则散落在 Controller 后调用可写大量字段的通用 `User.UpdateWithTx`。管理端资料修改走独立治理接口并复用校验器，不与本人权限混合。

### 5.3 资料头部与头像

资料头部固定为：

```text
[头像]  显示名称
        @用户名 • 已绑定邮箱 • 角色 • 邀请人邀请码
```

- 邮箱或邀请信息不存在时整项隐藏，不能产生空分隔符。
- 用户 ID、用户组和邀请人其他资料留在详情，不放入副标题。
- default 和 classic 都提供头像选择/上传和昵称编辑入口。
- 浏览器直传配置的第三方图床；CloveAPI 不接收图片二进制。
- 后端仅接受系统配置白名单中的 HTTPS 图片域名，拒绝任意外链、本地路径、内网地址和非图片结果。
- 图床失败或返回非白名单 URL 时不更新头像；更换头像只解除旧 URL 引用。

### 5.4 封禁理由

封禁操作支持用户可见理由和仅管理端可见的内部备注。用户可见理由存在时显示 `账号已被封禁：<理由>`，否则显示通用联系管理员提示。解封后不再展示旧理由，但历史审计继续保留。封禁、解封均按角色层级校验并记录操作者、目标、理由、来源 IP、请求 ID 和结果。

## 6. 邀请码申请审批制度

### 6.1 制度替换与保留项

普通用户升级后不再自动拥有可用邀请码。旧 `users.aff_code` 立即停止作为新注册凭据，只保留既有邀请关系和历史展示，不自动迁移为新邀请码。

以下既有能力继续保留：

- `inviter_id` 邀请关系；
- 注册是否必须填写邀请码的系统开关；
- 邀请成功后的双方奖励和合规开关；
- 已建立邀请关系的历史统计与归属记录。

注册开关关闭时允许不填邀请码；一旦填写就必须是新制度下的有效邀请码，无效码不能静默忽略。注册开关开启时，只接受已审批、未撤销、未过期且仍有次数的新邀请码。

### 6.2 用户流程

钱包新增邀请码区域：

1. 没有有效邀请码和待审批申请时，用户填写申请理由并提交。
2. 同一用户最多有一个待审批申请；待审批时可主动撤回。
3. 拒绝结果必须向申请人显示原因；拒绝后 24 小时才能重新申请。
4. 获批后显示类型、已用/总次数、到期时间、邀请码和注册链接。
5. 用户可复制邀请码、复制注册链接、查看自己的邀请使用记录。
6. 注册链接旁使用二维码图标作为入口；点击打开二维码弹窗，可下载 PNG。
7. 二维码由浏览器根据注册链接即时生成，不写数据库、不上传服务器。
8. 邀请码耗尽、过期或被撤销后，用户可重新申请。

同一用户最多拥有一个当前有效邀请码和一个待审批申请。申请创建、审批发放和发放后撤销都必须在事务内读取并更新申请/邀请码状态；MySQL/PostgreSQL 使用 `lockForUpdate(tx)` 锁定目标用户行，SQLite 依靠写事务和下述可空唯一活动槽位收敛并发。不能只依赖“已有申请记录”或页面状态。

### 6.3 管理员入口与审批

管理员导航在用户管理相关区域新增“邀请码”，包括三个视图：

- **申请审批：** 申请人、角色、理由、申请时间、状态、审批操作和拒绝原因。
- **已发放邀请码：** 所有者、类型、使用次数、有效期、状态、发放人和创建时间。
- **使用记录：** 邀请码、邀请人、注册用户、注册时间、奖励结果和来源。

审批通过时必须选择：

- **一次性：** 固定 1 次；
- **多次使用：** 2 至 100 次；
- **有效期：** 必填，最长 365 天。

拒绝必须填写原因。Admin/Root 可在相同权限规则下直接向目标账号发放，无需伪造用户申请；直接发放也必须填写管理理由并记录审计。

权限规则：

| 操作者 | 可审批/发放对象 | 禁止对象 |
| --- | --- | --- |
| Admin | 普通用户 | 自己、Admin、Root |
| Root | 普通用户、Admin | 自己、其他 Root |
| 用户 ID=1 | 任意账号，包括自己 | 无额外对象限制 |

所有权限由服务端根据操作者和目标的当前角色计算；审批过程中目标角色变化时必须按最新角色重新校验。

### 6.4 数据模型

新增三个独立表，避免继续扩张 `users.aff_code`：

#### `invite_code_applications`

- `id`、`user_id`；
- `reason`；
- 可空唯一 `pending_user_slot`：待审批时等于 `user_id`，进入任何终态时置空；
- `status`：`pending`、`withdrawn`、`approved`、`rejected`；
- `reviewer_id`、`review_reason`、`reviewed_at`；
- `created_at`、`updated_at`。

#### `invite_codes`

- `id`、`owner_user_id`、唯一 `code`；
- 可空唯一 `active_owner_slot`：有效时等于 `owner_user_id`，进入耗尽、过期或撤销终态时置空；
- `kind`：`single`、`multi`；
- `max_uses`、`used_count`；
- `status`：`active`、`exhausted`、`expired`、`revoked`；
- `expires_at`；
- `issued_by`、可空 `application_id`；
- `created_at`、`updated_at`、可空 `revoked_at`。

#### `invite_code_uses`

- `id`、`invite_code_id`；
- `inviter_user_id`、`registered_user_id`；
- `registered_at`；
- 奖励处理状态和必要的脱敏审计关联标识。

`invite_code_id + registered_user_id` 必须唯一。三种目标数据库的唯一索引都允许多条 `NULL`，因此 `pending_user_slot` 和 `active_owner_slot` 用普通可空唯一索引实现“一个待审批/一个有效码”，终态记录仍可无限保留。事务、支持数据库的行锁、唯一槽位和状态条件更新共同保证并发，不依赖部分索引。

### 6.5 注册事务与状态机

新增深模块 `InvitationRegistration`，密码注册、OAuth、微信和管理员创建用户等所有入口只能通过该模块消费邀请码，不能各自组合“查码 + 创建用户”。模块在同一主数据库事务内：

1. 精确查找新邀请码并锁定记录；
2. 校验 `active`、有效期和 `used_count < max_uses`；
3. 创建用户并写入 `inviter_id`；
4. 写 `invite_code_uses`；
5. 条件递增 `used_count`，达到上限时转为 `exhausted`；
6. 写入以 `invite_use_id` 为幂等键的奖励/通知 outbox 事件；
7. 提交后由消费者通过 `WalletLedger` 发放双方奖励并更新邀请统计。

只有注册事务成功才消耗次数。用户名冲突、验证码失败、用户创建失败或事务回滚都不能扣次数。MySQL/PostgreSQL 的锁使用项目 `lockForUpdate(tx)`，SQLite 通过写事务和条件更新保证；不得使用被 GORM v2 忽略的旧锁写法。

当前 `finishInsert` / `FinalizeOAuthUserCreation` 中提交后直接增加奖励的非幂等路径必须停止处理新邀请码。奖励消费者按 `invite_use_id + reward_side` 唯一键写账本，进程中断后可重试且不会丢失或重复发放；通知失败不回滚注册和奖励，但进入可观察重试状态。

过期状态可在读取时归一化并由后台任务持久化；撤销、耗尽和过期都是终态，不恢复原码。审批、拒绝、撤回、直接发放、撤销、成功使用和奖励结果全部写业务审计，但不记录注册密码、Cookie 或其他凭据。

## 7. Token 与钱包

### 7.1 余额口径

公共 Token 余额查询的主余额只能是用户钱包当前可消费额度：

- 不把活跃订阅剩余额度加到钱包主余额；
- `token_callable_quota` 单独表示 Token 状态、Token 限额、用户状态和钱包额度共同约束后的可调用额度；
- 订阅只作为辅助模块展示计划、状态、总额、已用和剩余；
- 后端返回明确分项快照，default/classic 不自行混算钱包、订阅和 Token 限额。

余额进度条、限制说明和钱包统计在两套前端使用相同公式和边界测试。

#### 7.1.1 WalletLedger 模块

当前代码只有 `users.quota` 余额和可能经过异步缓存/批量更新的增减函数，不存在可供用户兑换码复用的钱包账本。实施前先新增深模块 `WalletLedger`，其接口隐藏余额行锁、非负校验、账本写入、幂等和提交后缓存同步：

- `wallet_ledger_entries` 保存 `id`、`user_id`、唯一 `operation_id`、业务类型、整数 `delta`、变更后余额、关联对象类型/ID、创建时间和脱敏上下文；
- `AdjustWithTx(tx, userID, delta, operationID, category, reference)` 在同一主库事务中锁定用户、条件更新余额并写账本；
- 相同 `operation_id` 重试返回第一次结果，不重复扣款或入账；余额不足返回稳定业务错误；
- Redis/内存缓存只在事务提交后失效或同步，不能先于数据库修改；
- 用户兑换码、邀请奖励及后续新增资金动作必须使用该模块，不得调用现有非幂等 `IncreaseUserQuota` / `DecreaseUserQuota` 拼装事务。

账本从功能上线时开始记录，不伪造上线前历史；既有消费/充值日志继续作为历史来源。钱包页面可分别展示新账本和既有历史，不能把不完整账本标成全量历史。

### 7.2 用户自定义 API Key

自定义 Key 是用户为自己的 CloveAPI Token 指定的完整访问字符串，不是上游供应商凭据。

- 只有当前认证用户可在创建自己的 Token 时填写；Admin/Root 不能代替他人设置或修改。
- 创建后字符串不可编辑，只能禁用/删除后重新创建。
- 长度 16 至 128，只允许 ASCII 字母、数字、`_`、`-`，不强制 `sk-` 前缀。
- 自定义 Key 沿用分组、模型、钱包、订阅、IP、过期、额度和审计规则。
- 认证必须完整精确匹配；兼容层最多移除一次 `sk-` 前缀后再次完整匹配，不能按连字符截断。
- 数据库唯一约束是并发创建的最终防线；完整 Key 不得进入日志、审计、指标标签或 Redis key。

#### 7.2.1 Key 存储与分阶段迁移

Token 表同时保存：

- 由服务端密钥计算的规范化 Key HMAC 指纹，用于认证查找、唯一性和碰撞检测；
- 使用服务端密钥加密的 Key 密文，仅用于所有者 reveal；
- 脱敏展示指纹和密钥版本，不保存可逆明文。

认证路径按规范化输入计算 HMAC 后查找并做常量时间校验，不需要解密。加密/HMAC 主密钥来自稳定的专用服务端环境配置，不使用开发环境每次启动随机生成的默认 `CRYPTO_SECRET`，不存入普通 Option 表、不经设置 API 返回、不提交仓库。

迁移按四阶段执行，不能一次启动就清空旧 `tokens.key`：

1. 新增指纹、密文、密钥版本和脱敏前/后缀列；启动时校验专用密钥稳定可用；
2. 新建/更新 Token 双写旧列和新列，后台分批回填现有 Token，记录数量和失败 ID，不记录 Key；
3. 认证改为新指纹优先、旧明文兜底，持续核对命中结果；所有活跃记录回填并验证后停止旧列写入；
4. 最后版本才清除明文值。无法安全迁移的记录保持旧读或明确停用，不能静默使所有 Token 失效。

密文记录带密钥版本；轮换期间可读取当前和上一版本并在成功访问时重加密，只使用当前版本创建新记录。服务端密钥缺失、版本不支持或轮换失败时拒绝敏感操作，不能退回新明文存储。

Key 搜索改为：名称继续模糊搜索；完整 Key 使用 HMAC 精确搜索；脱敏前 4 位或后 4 位使用专用前/后缀列筛选。取消任意中间片段和 `%` 通配符搜索，不能为保留模糊搜索继续存明文。

### 7.3 完整 Key 多次查看

Token 所有者可以多次查看自己 Token 的完整值，此行为是明确保留的产品能力：

- 列表和普通详情默认始终脱敏；只有点击“查看完整 Key”才调用独立敏感读取接口。
- 接口必须校验当前登录用户就是 Token 所有者；Admin/Root 也不能借管理权限查看其他用户的完整 Key。
- reveal 前必须验证当前账户密码；成功后建立独立的 30 分钟 `token_reveal_verified_at` 窗口，窗口内可查看或批量获取自己的所有 Key，过期后再次触发才重新验证。
- 没有密码的 OAuth/Passkey 用户必须先设置密码。首次设置密码要求当前登录会话和已绑定邮箱验证码；没有已验证邮箱时先绑定邮箱。管理员不能代设密码。
- 眼睛图标、复制/批量复制、聊天预设、Fluent 填充、Dashboard 示例等所有会把完整 Key 返回浏览器的入口统一使用该窗口，不能保留旁路。
- 每一次请求，无论成功、拒绝或限流，都按用户、来源 IP 和 Token ID 执行严格短窗口限流。
- 每一个实际返回的 Token 都写独立 `token.secret_reveal` 敏感读取审计；批量返回多少个就记录多少个，另写批次摘要。事件记录操作者、Token ID、脱敏指纹、IP、请求 ID、结果和时间，不记录完整 Key。
- 成功 reveal 必须先持久化对应 outbox 事件再返回明文；outbox 无法写入时拒绝 reveal，确保不存在不可追踪的成功读取。
- 成功响应禁止缓存，使用 `Cache-Control: no-store`，前端不写 localStorage/sessionStorage，不在 URL、错误或遥测中包含完整值。
- 前端只在内存保存窗口内已取值；窗口到期、登出或账号安全状态变化时清空所有完整 Key。复制操作只使用当前内存值。

### 7.4 碰撞即疑似泄露

用户提交的自定义 Key 与任何现有有效 Token 精确碰撞时：

1. 请求者只得到统一的不可用提示，不获知 Token 所有者或碰撞原因；
2. 原 Token 在幂等事务中标记为疑似泄露并由系统禁用；
3. 原 Token 不能手动重新启用，所有者必须创建替代 Token；
4. 只记录 Token ID、脱敏指纹和请求来源的安全审计；
5. 向原所有者发送一次泄露提醒；
6. 重复碰撞不得重复发信或重复写同一处置事件。

## 8. 用户兑换码

### 8.1 与管理员兑换码并存

现有管理员 `redemptions` 表和管理功能原样保留。用户兑换码使用独立表、API、导航入口和权限，不把两套码混入同一状态机。

用户可以从钱包可用余额创建：

1. **一次性公开码：** 固定额度，任一符合条件用户成功领取后结束；
2. **拼手气红包：** 创建者设置总额度和领取人数，每位用户最多领取一次，最后一位领取剩余可分配额度。

领取仅面向已登录、未封禁且满足系统兑换条件的用户；创建者可以领取自己创建的码，仍受每人一次和状态条件约束。所有用户兑换码必须设置有效期，最长 30 天，不允许永久有效。金额、份数和有效期必须由服务端设置合理上下限。

拼手气红包的每次额度使用服务端密码学安全随机数，在剩余总额、剩余份数和最小可分配单位约束下生成；最后一人领取全部余量。不能使用 `math/rand`、客户端随机值或可由用户预测的种子。一次性码和红包都不允许分配零额度，低于最小单位时创建请求直接拒绝。

### 8.2 数据模型

新增：

#### `user_redemption_codes`

- `id`、唯一 `code`、`creator_user_id`；
- `kind`：`single`、`random_packet`；
- `total_quota`、`claimed_quota`、`refunded_quota`；
- `max_claims`、`claim_count`；
- `status`：`active`、`completed`、`cancelled`、`expired`；
- `expires_at`、`created_at`、`updated_at`、终态时间；
- 钱包预扣和退款的幂等关联标识。

#### `user_redemption_claims`

- `id`、`redemption_code_id`、`claimer_user_id`；
- `quota`、`claimed_at`；
- 入账状态和钱包账本关联标识。

`redemption_code_id + claimer_user_id` 唯一。额度使用整数 quota，不用浮点保存。新建的 `WalletLedger` 模块承载预扣、领取入账和退款，业务记录保存稳定幂等键；不得误用当前异步余额增减函数。

### 8.3 资金与状态机

- **创建：** 在事务内锁定创建者钱包，校验余额后一次性预扣总额度，再创建可领取记录。
- **领取：** 锁定兑换码，校验状态、有效期、重复领取和剩余份数，确定本次整数额度，写领取记录并给领取者入账。
- **随机分配：** 为剩余领取者保留最低可分单位，最后一人领取全部余量；统一使用项目 quota 转换/舍入工具，不裸转浮点。
- **取消：** 创建者可取消自己的有效码；已领取部分不回滚，只退未领取余额。
- **过期：** 读取路径可识别过期，后台任务负责终态化并退款；多实例重复执行仍只能退款一次。
- **异常恢复：** 任一步失败整笔事务回滚，不能出现先扣款后无记录、已领取未入账或重复退款。

状态条件更新、唯一约束、钱包账本幂等键和行锁共同防止并发双领。创建、领取、取消、过期和退款都写业务审计与用户可查账本。

### 8.4 用户与管理员入口

- 钱包提供“创建兑换码”和“兑换”动作。
- 个人导航新增“我的兑换码”，展示完整兑换字符串、类型、总额、已领/剩余、份数、有效期、状态、退款状态和领取详情。
- 用户可复制、查看详情、取消自己的有效码，不能查看其他创建者的码。
- 管理员现有兑换码区域新增“用户兑换码”视图，可按创建者、状态、模式、时间、到期和退款状态筛选。
- Root 可查看完整领取明细并执行禁用/取消等管理动作；Admin 的对象范围服从用户管理层级。
- 敏感详情读取、禁用、取消和退款全部写读取或管理审计。

## 9. 验证码邮件模板中心

### 9.1 模板规则

系统提供一个代码内置、不可删除的默认验证码模板和任意数量的自定义模板。自定义模板字段包括：

- `id`、显示名称、邮件主题、HTML 正文；
- `enabled`、`is_default`、排序值；
- 创建者、更新者和创建/更新时间。

只允许三个变量：`{{code}}`、`{{site_name}}`、`{{expiration_minutes}}`。保存时拒绝未知变量、空主题、空正文、超长内容和无效基础 HTML。变量替换使用明确解析，不执行模板表达式、脚本或任意函数。

最多一个启用且有效的自定义模板可以作为活动默认模板。发送验证码时按以下顺序选择：

1. 启用、标记为默认且校验有效的自定义模板；
2. 代码内置默认模板。

活动模板被禁用、删除、清空、损坏或读取失败时自动回退内置默认模板，不能阻断验证码发送。内置模板始终在设置页可见，可复制为自定义模板，但不可编辑或删除源模板。

升级迁移读取现有单值 Option `EmailVerificationTemplate`：非空且通过新变量/HTML 校验时，导入为第一条启用的活动自定义模板；为空时不创建自定义记录；无效时保留原 Option 供管理员查看并使用内置默认模板，同时在迁移报告中提示修复。确认新模板运行稳定后才停止旧 Option 读取，不能升级后静默丢失站点已有邮件内容。

### 9.2 管理体验

Root 设置页提供模板列表、新建、复制、编辑、删除、启用、排序、设为默认、实时预览和测试发送。预览使用明确模拟值，并在隔离 sandbox 中渲染经过允许标签/属性过滤的 HTML，避免模板脚本进入管理页面上下文；测试发送允许指定目标地址，使用模拟验证码并按操作者和 IP 限流。

模板及相关 SMTP 设置通过原子批量提交，防止界面显示已保存但运行时仍使用半套配置。SMTP/Tavily 等服务端密钥的返回值始终脱敏。测试发送设置连接、读取和总超时，错误只返回可操作的脱敏说明。

## 10. 业务审计、日志与 IP 安全

### 10.1 审计模型

审计按业务动作记录，不按页面访问记录。每条事件至少包含：

- 稳定事件类型和结果；
- 操作者和目标对象；
- 发生时间、来源 IP、请求 ID；
- 必要且脱敏的业务上下文。

必须覆盖：

- 注册、登录成功、登录失败、退出；
- 资料、用户名、头像、密码、2FA、Passkey、邮箱等安全设置变化；
- Token 创建、更新、查看完整 Key、禁用、删除、碰撞处置、认证/IP 限制拒绝；
- 充值、扣费、退款、余额转移和用户兑换码资金动作；
- 邀请申请、审批、拒绝、直接发放、撤回、撤销、注册使用和奖励；
- 角色、Root、封禁/解封和用户管理变更；
- 系统设置、渠道、模型和邮件模板变更；
- 管理员查看用户安全详情、完整 IP、敏感详情和导出；
- Playground 搜索路径/失败、生图请求及结果状态；
- 后台自动退款、订阅重置、配置重载、外部依赖失败和恢复。

登录失败事件必须在身份未建立时也能记录尝试标识的安全散列/脱敏值、IP、请求 ID、失败类别和结果；不得记录明文密码、验证码或可用于账号枚举的额外响应差异。

不记录纯页面访问、静态资源、无业务意义刷新、健康检查或监控探针。任何事件不得包含密码、完整 Token、Cookie、Authorization、Tavily Key、SMTP 凭据、完整提示词、搜索查询全文、图片二进制或敏感原始请求体。

#### 10.1.1 关键审计 outbox

资金、角色、封禁、邀请码、Token 泄露处置和敏感凭据读取等关键事件不能依赖“业务提交后再尽力写日志”。主数据库新增可移植的 `audit_outbox_events`：

- 关键业务变更与对应 outbox 事件在同一主库事务提交；
- 每个事件使用全局唯一 `event_id`、稳定事件类型、脱敏 payload、创建时间和投递状态；
- 后台投递器以至少一次语义写入审计库；主库投递凭证按 `event_id` 唯一，SQLite/MySQL/PostgreSQL 日志库可增加唯一事件列；
- 投递成功后条件更新 outbox 状态，失败按退避策略重试并暴露积压指标和告警；
- 不允许因审计库暂时不可用而回滚已经安全提交的钱包领取，也不允许将未投递事件静默删除。

登录失败等没有主业务写事务的事件也先写主库 outbox，再异步投递。普通低风险观测日志可继续使用现有非事务路径，但必须与关键审计事件类型清楚区分。

独立 `LOG_SQL_DSN` 可能指向 ClickHouse，而现有 `MergeTree` 不提供普通唯一约束。ClickHouse 路径不能宣称数据库唯一幂等：投递器在主库维护确定性投递凭证，日志记录携带 `event_id`；若写成功但确认状态丢失导致重复，查询/导出按 `event_id` 去重，或迁移到明确支持该语义的 `ReplacingMergeTree`。实现计划必须覆盖 SQLite/MySQL/PostgreSQL 同库日志和 ClickHouse 独立日志两种部署。

### 10.2 四类记录体验

绘图日志、任务日志、合规确认记录、来源归属确认记录统一采用使用日志页的数据体验：

- 类别筛选、日期范围和管理员范围切换；
- 列显隐、桌面表格、移动卡片；
- 服务端分页、页码跳转、前后翻页和每页行数；
- URL 保存类别、筛选、日期、页码和每页行数。

底部 `总计：N` 必须由后端按当前完整筛选条件执行真实 `COUNT(*)`，不能使用当前页长度或 10,000 条截断。数据库查询失败必须返回明确错误，不能伪装为空列表或 `总计：0`。

### 10.3 IP 数据来源

系统补齐并区分：

- 普通注册 IP；
- 登录成功与失败 IP、最近登录 IP和历史；
- API 调用 IP 聚合和事件历史。

IPv4 与 IPv6 分别标准化、聚合、筛选和展示，不强行合并不同协议、网段或 IPv4 映射 IPv6。`c.ClientIP()` 只有在 `TRUSTED_PROXIES` 正确配置时可信；管理页面在代理配置风险存在时显示管理提示。

### 10.4 全局与用户安全详情

保留全局 IP 审计表，并在用户行操作中新增独立“安全与 IP 审计”入口，不能把敏感 IP 混入通用用户编辑响应。

- Admin 只能查看其可管理普通用户的风险摘要、掩码 IP、关联数量和异常计数。
- Root 可查看权限范围内的完整 IP、历史、关联用户以及注册/登录/API 调用时间线。
- 查看完整 IP 或关联账号属于敏感读取，必须审计。
- 默认范围近 30 天，可切换近 7 天、30 天、90 天、全部历史或自定义日期。
- 页面支持关联账号数和列表、调用/错误/登录次数、近期异常和最近活动。

后端必须先做对象层级校验，再裁剪字段；不能先返回完整数据后让前端掩码。

## 11. Playground

### 11.1 顶层模式和会话状态

Playground 顶层只有“聊天”和“生图”两个 Tab：

- 聊天和生图分别保存模型、草稿和参数，切换时互不覆盖；
- 状态只保证当前浏览器页面会话，刷新后不承诺恢复；
- 聊天继续走 `POST /pg/chat/completions`；
- 生图走独立 `POST /pg/images/generations`，由现有 Relay 执行用户、分组、渠道、额度和模型路由；
- 任何外部服务密钥都不返回浏览器。

### 11.2 聊天附件

default 与 classic 已经支持本地图片、文本和常见文档附件，实施不能回退该能力：

- 选择或粘贴图片，在浏览器转换为 `data:image/...;base64,...`，构造 OpenAI 兼容的 `image_url` content part；
- 读取 `.txt`、`.md`、`.json`、`.csv`、`.tsv`、`.log`、`.yaml`、`.yml`、`.xml` 和 `text/*`，以有边界标记的文本上下文拼入用户消息；
- 使用现有 `pdfjs-dist`、`mammoth` 和 `@e965/xlsx` 在浏览器提取 PDF、DOCX、XLS/XLSX/ODS 文本，按页或工作表标记后作为文本上下文；
- 附件条目显示文件名、大小、缩略图和移除操作；
- 图片数量/单张大小、文本/文档数量、单文件大小和总字符数沿用两套前端已有一致限制；
- 压缩包、可执行文件和其他未实现解析的二进制文件明确拒绝，不能假装上传成功；
- 大型 base64 不写 localStorage 或长期会话历史，发送完成后按产品交互释放不再需要的对象 URL。

### 11.3 联网搜索

联网是聊天工具栏能力，不是顶层模式。用户选择 `off`、`basic`、`advanced`，默认 `off`。

处理顺序：

1. 后端根据模型和渠道能力判断是否支持原生联网；
2. 支持时透传对应兼容字段，路径标记为 `native`；
3. 不支持且 Root 已启用 Tavily 时，由服务端调用 Tavily，路径标记为 `tavily`；
4. Tavily 结果按配置限制数量、响应体和上下文字符数，以带来源编号的事实参考注入模型上下文；
5. 未配置、超时、取消、无结果或上游失败时不注入伪造内容，向用户明确返回未联网状态。

用户选择必须真实控制 Tavily：`basic` 使用 basic 深度，`advanced` 使用 advanced 深度；不能像当前实现一样只改变搜索上下文尺寸却继续使用 Root 默认深度。原生联网能力由模型和实际路由渠道能力共同决定，Root 模型模式仅作覆盖，不是唯一真相。

第一版使用内部 `SearchProvider` 接口并只实现 Tavily。Root 设置包括启用、API Key、默认深度、最大结果数、最大上下文长度以及原生联网模型/渠道能力映射。Tavily 客户端设置短连接/读取/总超时、响应上限、取消传递和脱敏错误。

Playground 流式协议增加专用 metadata 事件，至少包含搜索状态、路径和最多 5 个来源的标题、URL、摘要/域名。后端必须把实际 `PlaygroundSearchOutcome.Sources` 放入事件，不能只保存来源数量到 Gin context；default/classic 流解析器都要识别该事件并写入消息来源字段。前端根据 metadata 生成可点击来源卡片，不能从模型正文猜测来源。普通 OpenAI 兼容 Relay 响应不受该 Playground 专用事件影响。

审计只记录用户、模型、`native/tavily/failed/off` 路径、来源数量、耗时和结果，不记录搜索全文、提示词、来源正文或 Tavily Key。

### 11.4 思考强度

聊天工具栏提供关闭、低、中、高，默认关闭。前端根据当前模型能力显示或禁用，后端仍要再次校验：

- OpenAI 兼容模型映射为 `reasoning_effort`；
- 其他渠道映射为已有预算或厂商字段；
- 不支持的模型不发送任何思考字段，并对伪造请求返回稳定校验错误；
- 切换到能力不同的模型时保留用户选择意图，但提交 payload 必须以当前模型实际能力为准。

### 11.5 生图

生图模型候选是“当前用户组实际可路由图片 endpoint 模型”与“Root 配置允许范围”的交集。Root 可配置允许列表、禁用列表、额外显式允许模型、排序和能力参数；无可用模型时明确提示配置或用户分组问题，不能像当前 default 草稿一样回退到选中的文本模型或全部模型。

聊天和生图分别维护 `chatModel/chatDraft/chatParams` 与 `imageModel/imageDraft/imageParams`。当前 default 共用 `config.model` 的实现必须拆开，classic 新增同等聊天/生图 Tab、联网和思考强度控制。

表单包括提示词、模型、尺寸、数量和输出格式；质量、风格、背景/透明度只在模型支持时显示和发送。数量遵守项目图片请求上限和计费安全规则。

结果仅存在当前浏览器会话：URL 可预览、复制和下载；Base64 转临时对象 URL，替换结果或卸载页面时释放。不写数据库、不创建永久图库。失败时保留表单，区分取消、超时、额度不足、无路由和上游拒绝并允许重试。

### 11.6 外部服务验收

Tavily、图片上游和 SMTP 均使用本地可控假服务做成功、超时、无结果、非法响应、取消和上游错误测试。验收不能依赖真实付费密钥，也不能将测试密钥提交仓库。

## 12. Snow 首页

### 12.1 路由与应用外壳

Snow 只作为根路径 `/` 的可选首页内容：

- `HomePageMode=default` 使用 New API 原首页；
- `HomePageMode=snow` 在 default/classic 各自应用外壳内加载 `/snow-assets/`；
- 登录、注册、控制台、后台、文档、模型广场及所有其他 SPA 路由继续使用原应用；
- SPA history fallback 始终返回当前 default/classic 应用入口，不能因 Snow 模式返回 Snow index；
- `/snow-assets`、`/snow-assets/` 和 `/snow-assets/assets/**` 使用独立命名空间，不占用应用 `/assets/**`。

### 12.2 原生导航和滚动循环

- Snow 不提供替代全站导航；页面顶部必须是 default/classic 原生导航。
- default 保留原导航从展开态滚动收缩到居中胶囊态的行为，classic 保留其原有对应行为。
- Snow iframe 的同源滚动状态驱动外层导航；消息/事件必须验证来源和数据格式。
- Snow 原叙事循环必须保留：持续向下滑动回到初始雪屋场景时，外层导航同步恢复初始展开态；离开开场区域后再次按原逻辑收缩。
- 导航状态只由当前首页滚动控制，离开首页后不残留 Snow 状态。

### 12.3 布局与交互

- 首页主体和 iframe 从视口顶部铺满，`body`、`main`、iframe 不能产生大白边、默认 margin、行内基线缝隙或额外固定导航占位。
- 桌面、窄桌面和 390px 移动视口不得出现品牌/导航重叠、不可点击控件或横向裁切。
- Snow 内部 CTA 使用当前站点相对路由并在父应用中导航，不硬编码域名，不将用户困在 iframe。
- iframe 提供可访问标题；降级/加载失败时提供返回 New API 原首页或关键应用入口的可用状态。

### 12.4 资源与性能

Snow 首页主体已经完成：实际冷启动可显示雪屋，向下滚动后 New API 原生导航会居中收缩，页面无大白边，其他应用路由不受影响。后续计划不得以“恢复 Snow 源工程”为实施前置条件，也不重建已经完成的页面。

`web/snow/dist/**` 当前为 111 个文件、约 18.99 MiB，是运行和 `go:embed` 的 vendored 静态依赖，必须完整纳入源码提交并提供文件清单。收尾范围限定为：

- 把 Website、Console、Playground 等硬编码外部站点改为当前父站相对路由，Docs 使用 `/api/status` 的配置；
- 静态哈希资源设置长期缓存，入口 HTML 不长期缓存；
- 保留现有雪屋、滚动循环、导航同步、声音和视觉资源，不以 8 MiB 或源码级懒加载作为本轮交付门槛；
- fresh load、持续滚动、完整循环和至少 10 分钟运行态均检查 canvas 非空和控制台错误；此前单个旧标签出现的 Three.js 栈溢出作为回归观察项，只有可稳定复现才进入修复；
- 性能数据继续记录为观察指标，不能为了追求数字直接编辑大段压缩逻辑或破坏现有体验。

## 13. 数据库与迁移

- 新表通过 GORM `AutoMigrate` 和必要的可移植迁移创建，支持 SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6。
- 新表至少包含邀请码三表、`wallet_ledger_entries`、用户兑换码及领取表、邮件模板表和关键审计 `audit_outbox_events`；Token 新增指纹/密文/版本/脱敏前后缀列。每个状态字段、幂等键和唯一约束都要有对应迁移测试。
- 不使用数据库专属 JSON、部分索引、枚举或锁语法作为唯一正确性保障。
- 需要行锁时统一使用 `lockForUpdate(tx)`；SQLite 使用事务、唯一约束和条件更新兜底。
- 金额和额度使用整数及 `common.QuotaFromFloat`、`common.QuotaRound` 等统一工具，不做无界裸转换。
- 新数据库初始化和从当前旧数据库升级都必须测试；重复启动迁移保持幂等。
- 旧 `users.aff_code`、`invite_limit_mode` 和 `invite_limit_count` 只作迁移兼容/历史读取，不参与新邀请码的申请、发放和注册次数判断；前端不再把旧人数上限作为现行制度展示。
- 数据库迁移失败要阻止服务以半迁移状态继续运行。

## 14. API 契约与权限边界

实施计划可以按仓库既有路由命名调整具体 URL，但必须保持以下契约分区：

- **本人资料：** 获取资料、更新昵称/头像、返回冷却时间；
- **本人邀请码：** 申请、撤回、查看有效码、注册链接和使用记录；
- **管理员邀请码：** 申请列表、审批/拒绝、直接发放、已发放列表、使用记录和撤销；
- **本人 Token：** 创建、管理和独立 reveal 敏感读取；
- **用户兑换码：** 创建、领取、我的列表、详情和取消；
- **管理员用户兑换码：** 检索、详情、管理取消/退款；
- **邮件模板：** Root CRUD、排序、启用、默认、预览和测试发送；
- **用户安全详情：** 独立于通用用户详情，按角色返回掩码摘要或完整数据；
- **Playground：** 聊天流、生图请求和专用搜索 metadata。

列表响应统一返回数据、真实总数、页码和每页行数；写请求返回稳定机器错误码和可本地化消息。涉及审批、钱包、退款、状态迁移的重复请求使用稳定幂等键或状态条件，不能依靠按钮禁用防重。

所有对象级权限在 Service/Model 边界集中实现并被 Controller 复用。Controller 不得通过读取前端传来的角色、所有者或余额字段决定权限和资金结果。

## 15. 安全与故障处理

- Tavily、SMTP、上游密钥和授权头只存在于最小服务端范围；完整 Token 只在认证处理或所有者成功 reveal 的短生命周期内存/响应中出现，不进入通用数据接口和持久化明文。
- 系统设置 API 对已有密钥只返回“已配置”或掩码，不把原值回显到普通表单。
- 头像 URL 做协议、主机白名单和规范化校验，阻止内网/本地地址及绕过形式。
- 外部网络调用继承请求取消，设置连接、读取、响应大小和总超时；失败不能显示为成功。
- 高权限和资金操作先校验角色、目标、当前状态和幂等条件，再进入事务。
- 乐观更新冲突返回明确错误并要求刷新，不静默覆盖他人刚完成的管理修改。
- 错误响应不泄露数据库结构、外部密钥、Token 碰撞对象、SMTP 认证信息或内部网络地址。
- 审计写入失败必须被监控；关键事件统一通过主库事务 outbox 投递，关系型日志库按 `event_id` 幂等，ClickHouse 按主库投递凭证和查询去重保证语义，不能无声丢失。

## 16. 验收标准

### 16.1 用户、权限和邀请

- 普通用户可编辑合规昵称和白名单头像，昵称冷却由后端强制；`/api/user/self` 返回完整显示字段。
- 只有 ID=1 可提升/降级其他 Root，且不能降级自己；运行时不存在 `super_root`。
- 被封用户看到用户可见理由，内部备注不泄露。
- 用户能申请和撤回邀请码；Admin/Root 的审批对象严格符合角色矩阵。
- 一次性和 2–100 次邀请码遵守最长 365 天有效期；只有成功注册消耗一次。
- 同一用户的并发申请/发放通过支持数据库的用户行锁和三库通用可空唯一槽位，收敛为一个待审批申请和一个有效邀请码。
- 旧 `aff_code` 不能注册，新码仍正确建立 `inviter_id` 并触发现有奖励。
- 注册链接可复制，二维码由图标打开并能下载 PNG。

### 16.2 Token、钱包和兑换码

- 主余额等于钱包可消费额度，订阅不计入主余额。
- 自定义 Key 做完整匹配，不按连字符截断；碰撞处置只执行一次且不泄露对象。
- Key 通过分阶段迁移改为 HMAC 指纹和密文，迁移期间旧 Token 不失效；名称模糊、完整 Key 精确和前/后 4 位搜索可用，任意 `%` 片段搜索被移除。
- 所有者验证账户密码后，可在 30 分钟内通过查看、批量复制、聊天预设、Fluent 和 Dashboard 使用自己的完整 Key；每个返回值都有限流、`no-store` 和成功/失败审计，管理员不能查看他人的值。
- OAuth/Passkey 无密码用户通过登录会话和绑定邮箱验证码设置密码后，才能开启完整 Key 窗口。
- `WalletLedger` 的稳定 `operation_id` 保证新资金动作重试不重复，缓存只在事务提交后同步。
- 用户兑换码只从钱包预扣；并发领取、取消、过期退款不重复扣款、入账或退款。
- 创建者可按同一规则领取自己的码；拼手气额度使用密码学安全随机数且每份不低于最小单位。
- 用户只能管理自己的兑换码，管理员入口按对象层级裁剪。

### 16.3 邮件、日志和 IP

- 内置邮件模板始终可用；自定义模板可 CRUD、启用、排序、预览、测试发送并在无效时回退。
- 四类记录提供真实总计、完整筛选和服务端分页；查询失败不伪装为零结果。
- 登录成功和失败都产生脱敏审计。
- 资金、权限和敏感读取事件通过主库 outbox 投递；关系型日志库幂等写入，ClickHouse 重复投递可在查询层按 `event_id` 去重，并有积压告警。
- Admin 只见权限范围内掩码 IP 摘要，Root 可查看完整时间线；所有敏感读取有审计。

### 16.4 Playground

- default/classic 都能发送受限图片、文本、PDF、Word 和表格附件，拒绝压缩包及其他未支持二进制。
- 原生联网优先，Tavily 只作服务端降级；来源通过 metadata 形成卡片，失败不虚报联网。
- 思考强度只向支持模型发送正确参数。
- 生图不会回退文本模型，调用 `/pg/images/generations`，聊天/生图状态互不覆盖，结果只留当前会话。

### 16.5 Snow 与全站

- Snow 只出现在根首页，New API 其他导航和路由保持可用。
- 原生导航滚动后按既有方式收缩；Snow 循环回到雪屋开场时恢复展开状态。
- 无顶部/四周大白边、品牌遮挡和移动端横向裁切。
- 内部链接使用当前站点，全部 vendored 资源纳入 Git 且无 4xx；fresh load、循环滚动和 10 分钟运行态 canvas 非空，控制台无可复现致命错误。
