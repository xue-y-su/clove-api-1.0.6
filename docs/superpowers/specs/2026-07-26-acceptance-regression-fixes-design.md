# CloveAPI 验收回归修复设计

**日期：** 2026-07-26  
**状态：** 用户已确认设计，待编写实施计划  
**适用分支：** `recovery/production-restore-20260719`  
**基线提交：** `d83e088f`  
**关联证据：** `docs/superpowers/specs/2026-07-25-regression-evidence.md`

## 1. 目标与边界

本轮解决当前验收中仍可见的功能回归和交互缺陷，覆盖安全与 IP 审计、邀请与奖励、公告、游乐场、API Key、用户兑换码、个人资料和首屏性能。修复优先复用已经存在的模型、接口和页面，不另建重复模块。

明确不做以下内容：

1. 不接入百度 IP 画像 API，也不在服务器运行浏览器抓取百度页面。
2. 不新增“详细错误日志”数据库、错误中心或错误详情弹窗。
3. 不向普通用户展示渠道 ID、渠道名称、内部堆栈或上游鉴权信息。
4. 不把上游 `5xx`、`429`、参数错误或一般调用失败计入安全风险。
5. 不为已经有独立页面的功能再建立第二套页面或平行数据源。

## 2. 总体方案

采用“修正现有契约、保持单一事实源、按风险拆分视图”的方案：

- 安全与 IP 审计以 `IPAuditRollup` 为列表和关联查询的在线数据源，原始事件只用于分页详情。
- 邀请、公告、兑换码和 API Key 继续使用现有业务实体，通过补齐状态机和窄用途更新接口修复回归。
- 页面错误保持简洁具体，使用日志保持当前粒度，技术诊断只进入运行日志。
- Default 前端作为本轮主要验收界面；Classic 中存在同功能时保持后端契约和关键行为一致。
- 所有数据库变更必须同时兼容 SQLite、MySQL 5.7.8+ 和 PostgreSQL 9.6+。

## 3. 安全与 IP 审计

### 3.1 风险事实

安全审计只采集三类可验证事实；事实达到配置的时间窗口和阈值后才成为风险提醒：

| 风险事实 | 数据来源 | 展示重点 |
| --- | --- | --- |
| 共享注册 IP | 用户注册记录和注册类安全事件 | 真实注册账号数、首次和最近注册时间 |
| 共享调用 IP | API 调用类投影 | API Key 所属账号数、请求数、最近调用时间 |
| API `401 Unauthorized` | 最终调用结果 | `401` 次数、涉及账号数、时间范围 |

默认阈值为：24 小时内同一公网 IP 注册 3 个账号、24 小时内同一公网 IP 被 5 个账号用于 API 调用、10 分钟内同一公网 IP 出现 10 次 API `401`。系统设置键分别为 `ip_security.shared_registration_user_threshold`、`ip_security.shared_api_user_threshold` 和 `ip_security.unauthorized_threshold`；时间窗口固定为前述值，避免页面配置过度复杂。告警只用于排序和提醒，不能自动封禁账号、Token 或 IP。

共享调用 IP 可能是公司出口、代理或共享 Key。页面使用“需要核查”等中性描述，不直接定性为作弊。`5xx`、`429`、上游超时、参数错误、内容审核拒绝和其他普通失败不参与风险判断。它们仍按原有使用日志或运行日志规则记录，但不能把正常上游波动误报为账号安全问题。

### 3.2 查询与性能

1. 全局列表和用户页摘要只读取 `IPAuditRollup`，不得扫描整张 `ip_security_events` 或使用日志表。
2. 原始事件只在用户展开某个 IP、账号或时间线时按时间范围和游标分页读取。
3. 列表接口返回完整的 `total`、`page`、`page_size` 和是否还有更多数据，不能显示“300 个账号”却只允许查看固定的前 20 或 50 个。
4. 默认先按风险等级排序，再按最近活动时间排序；没有风险的普通活动放在后面。
5. 用户页 `clove · #1` 一类摘要首屏只返回必要聚合，不随历史事件总量线性变慢。

性能验收：在约 100 万条原始事件规模下，rollup 主查询目标小于 100ms，用户摘要接口本地 p95 小于 300ms，页面首屏不因详情查询阻塞。

### 3.3 页面信息架构

独立安全与 IP 审计页面保留，页面侧边的“查看”菜单提供：

1. 风险优先
2. 共享调用 IP
3. 共享注册 IP
4. 认证活动
5. 全部活动

风险行必须直接说明原因，例如“3 个账号通过此 IP 调用 428 次，其中 17 次返回 401”，不能只写“异常活动”。注册账号数、调用账号数、调用次数和 `401` 次数必须分开展示，不能合并为含义不清的“相关账号”。点击风险项展开账号归属、计数和时间线；时间线有 `request_id` 时可跳转到对应使用日志筛选结果。

当前操作者有权查看完整 IP 时，每个有效公网 IPv4 或 IPv6 后提供一个小型外链图标，点击后在新标签打开百度 IP 查询页面。掩码 IP、私有、回环、保留、链路本地或格式无效的地址不显示该按钮。按钮只负责跳转，不保存查询结果，也不宣称已接入百度数据。

IP 单元格使用稳定列宽、等宽字体和 `overflow-wrap:anywhere`。IPv6 可以换行，但不能覆盖风险徽标、账号数或操作列。新增下拉框统一使用项目现有 `Select` 组件。

### 3.4 权限与数据解释

- 保持现有 Root 完整 IP、普通管理员受限投影的权限边界，不因增加外链按钮扩大数据权限。
- API 调用中的账号表示 API Key 所属者；注册和认证事件中的账号表示直接执行该行为的账号。
- 不过滤 ID 1 或 Root 的真实调用事实，但必须通过“账号归属”字段说明它为什么出现在该 IP 下。
- 可信代理或 Docker 网关识别为基础设施地址后，从风险判断中排除，但仍可在“全部活动”中查看。

## 4. 邀请码与邀请奖励

### 4.1 邀请码状态

- 新生成邀请码固定为 10 位无歧义字母数字码，排除 `0/O`、`1/I/L` 等易混淆字符。使用加密随机数生成，数据库唯一索引兜底，发生碰撞时自动重新生成。
- 用户页同时显示邀请码和完整邀请链接；链接携带 `aff` 参数。
- 注册页读取 `aff` 后自动填充邀请码，并防抖调用校验接口。可用时显示绿色勾和明确文案，不可用时显示红色叉及不可用原因，但不暴露邀请码所属用户。校验接口按 IP 和设备限流，防止批量枚举。
- 邀请码已用尽、过期或被撤销且当前没有冷却时，根据申请开关显示“再次申请”。
- 若管理员关闭用户申请，页面明确显示“管理员未开放邀请码申请”，不能只隐藏按钮。
- 拒绝冷却到期后回到普通可申请状态，旧的红色拒绝主提示不再持续占据页面；历史拒绝记录仍保留供审计。

### 4.2 奖励与提现审批

逐笔奖励事实继续作为唯一奖励来源，但不再预先逐笔审批。用户钱包卡片展示：

- 成功邀请人数
- 累计奖励
- 可申请金额
- 审核中金额
- 已到账金额

奖励状态采用 `available -> pending_payout -> paid` 主流程。用户点击提现后创建一笔聚合提现申请，并在事务中锁定本次包含的 `available` 奖励项。管理员“邀请码审批”页面审批的是提现申请，而不是先审奖励再审提现：通过时恰好一次写入钱包并把奖励标记为 `paid`；拒绝时把奖励项退回 `available`。并发提交、重复审批和重复回调都不能二次入账。

历史 `pending_review` 和已通过但未提现记录迁移为 `available`，历史已提现记录迁移为 `paid`，历史已拒绝记录保持拒绝终态，不因迁移重新变成可申请。

邀请码卡片和邀请奖励卡片按自身内容高度布局，不再被同一网格行强制拉得过高。

## 5. 公告

### 5.1 每条公告独立弹窗

弹窗属性属于单条公告，不使用统一的“所有公告都弹窗”开关。新增或编辑公告时提供“进入网站后弹窗提示”复选框；未勾选的公告只出现在通知或时间线中。

- 未登录用户不弹公告。
- 登录态恢复、合规声明和来源归属门禁完成后，再判断是否存在未确认的弹窗公告。
- 每个用户对每个公告版本只需确认一次；公告正文、图片或发布时间变化后产生新签名，可再次弹出。
- 确认失败时保留弹窗并显示正常错误，不与合规确认状态串用。

### 5.2 内容与图片

- 取消 500 字符限制，正文按 UTF-8 字节计算，固定上限为 64 KiB，并在前端显示剩余容量。
- 内容统一由支持原生 HTML 的 Markdown 解析器处理，再对最终 HTML 执行统一白名单净化。因此纯文本、Markdown 和 HTML 可直接混用，不需要格式选择框。
- 白名单净化禁止脚本、事件属性、危险协议、内联框架及其他可执行内容。
- 管理员通过方形加号框上传 PNG、JPEG、WebP 或 GIF；不要求手填图床 URL。
- 单张图片上限为 5 MiB，解码后宽高均不得超过 4096 像素。
- 修复 `/data/announcement-media` 的启动期目录创建和归属，写入采用临时文件和原子重命名。
- 公告图片可点击打开灯箱查看大图，支持关闭、键盘 Escape 和移动端缩放适配。

通知和时间线切换时保留两个面板的查询缓存和稳定容器高度，避免卸载重建造成闪烁。

## 6. 游乐场

### 6.1 请求取消根因

图片模式出现 `canceled` 的根因是带 `AbortSignal` 的 GET 请求参与了全局 Promise 去重：聊天页取消自己的请求时，会连带取消图片页复用的同一个 Promise。

修复规则：带 `signal` 的 GET 不参与共享 Promise 去重；无 `signal` 的幂等 GET 仍可按现有规则合并。页面切换只能取消本组件发起的请求。

### 6.2 模型与图片参数

- 选择分组后只显示该分组真实可用模型，并提供搜索；切换分组清空不再可用的旧模型选择。
- 不再显示含义不明的“输出 URL”。协议内部仍可固定请求 URL 格式，但不能伪装成用户设置。
- 质量、背景、尺寸和数量等控件只有在请求构造器确实发送对应字段时才展示。
- 使用 `rightcode` 的实际模型验证非默认参数确实离开 CloveAPI；上游不支持时返回正常错误，不假装参数生效。
- 图像请求失败时保留提示词、模型、分组和参数，方便用户调整后重试。

### 6.3 联网搜索

联网搜索来源为空、接口失败或用户切换模式时均不得调用 `.map()` 等产生页面级 500 的路径。失败只影响当前请求，游乐场页面保持可操作，并显示简洁具体的错误和请求 ID。

## 7. API Key

### 7.1 分组快捷修改

新增或完善只更新分组的窄接口 `group_only`。服务端验证目标分组属于当前用户可用分组，只更新 token 的 `group` 字段，并记录现有管理/操作审计事件 `token.group_update`。

Key 列表中的分组徽章可点击，打开项目已有的 `ApiKeyGroupCombobox`。保存期间只禁用当前操作，不能用旧表单状态覆盖名称、额度、模型限制或其他字段。

### 7.2 自定义 Key 与状态

- 自然生成的 Key 继续保留标准 `sk-` 前缀。
- 只有用户明确填写的自定义 Key 不强制添加 `sk-`，也不删除用户输入的合法前缀。
- 自定义 Key 长度或字符不合法时返回具体校验原因，不能只显示“创建失败”。
- 碰撞处置导致禁用时，状态显示“疑似泄露”或等价安全状态，不仅显示“已禁用”。
- 状态徽章禁止收缩和省略，完整显示文字。

普通软删除 Key 时，在同一事务中把原 Key 替换为不可认证、不可逆的随机墓碑值，再写删除状态。这样保留审计记录并释放唯一索引，用户可重新创建相同自定义 Key；墓碑值不能恢复成原始密钥，也不能通过认证。

疑似泄露 Key 使用独立撤销指纹表保存 HMAC-SHA-256 指纹，复用现有 `TOKEN_HMAC_KEY`，不新增弱密钥或把密钥写入数据库。撞到活动 Key 时拒绝新建、禁用原 Key、写一次安全审计并保存撤销指纹；撞到撤销指纹时明确提示“该密钥曾被标记为泄露，不能再次使用”。普通删除不写撤销指纹，疑似泄露删除后也不能重新创建相同 Key。

## 8. 用户兑换码

### 8.1 自领与账务

允许创建者领取自己的兑换码。创建时额度已经从创建者钱包预留，因此自领只能把对应份额返还给创建者并消耗一次领取次数，不能新增系统额度。

普通模式和红包模式都遵循以下不变量：

- 钱包扣除、预留、领取、退款和作废总额守恒。
- 同一用户不能重复领取同一兑换码。
- 并发领取不能超过最大人数或剩余额度。
- 禁用只暂停领取，不处理剩余额度。
- 到期后进入 `expired_pending`，停止领取但继续冻结剩余额度，等待管理员决定退款或作废。
- 退款或作废是一次性终态操作，不能重复处理剩余额度。

状态转换固定为：

```text
active <-> disabled
active -> exhausted
active / disabled -> expired_pending
active / disabled / expired_pending -> refunded 或 forfeited
任意终态 -> deleted
```

`exhausted` 表示领取次数或剩余额度已正常用尽，不再执行退款或作废。只有未到期、未耗尽、未删除且未进入资金终态的 `disabled` 兑换码可以重新启用。管理员对活动兑换码执行删除时，界面必须先要求选择退款或作废，服务端在同一事务中完成资金终态和删除；删除本身不能再次触发退款。

### 8.2 创建和管理界面

- 用户创建金额使用钱包标准金额换算，不复用旧积分比例或单次请求计费的 `int32` 边界。
- 大额无效时明确说明是单次金额、总金额、领取人数、最小单份或余额中的哪个条件不满足。
- 创建成功后的复制按钮必须使用实际生成的 code，并提供复制成功或浏览器权限失败反馈。
- 管理员“用户兑换码”页继续审计所有用户创建的兑换码，可查看详情、领取记录、禁用、启用、删除和按策略终止。
- 管理员列表默认将 `expired_pending` 置顶并显示待处置数量，支持筛选以及批量“退款”或“作废”。批量操作对每个兑换码分别执行幂等事务，并返回逐项成功或失败结果，不能因其中一项失败而隐藏其他项的处理状态。
- 用户侧在创建按钮旁使用紧凑的“我的兑换码”入口，通过弹窗查看本人创建的兑换码和领取情况，不新增重复侧边栏页面。
- 用户领取兑换码只在钱包现有兑换入口进行，“我的兑换码”弹窗不放第二个领取入口。
- 所有模式和状态选择使用 New API 现有 `Select` 样式。

## 9. 个人资料

- 顶部资料卡右侧保留小型编辑按钮，点击后在弹窗中修改昵称和头像；不在页面下方重复放置资料编辑表单。
- 顶部灰色摘要只显示值，例如 `@clove · Admin`；存在邀请人时再追加邀请人值，没有邀请人则完全不显示该段，不显示“用户名”“用户分组”“邀请人”等前缀。
- 昵称冷却期间仍允许打开编辑弹窗和修改头像。只禁用昵称字段，并显示下次可修改的准确时间。
- 头像上传沿用“浏览器上传到配置图床，服务器只保存经允许域名校验的 URL”的设计；修复请求挂起和 `Failed to fetch`，并保留可理解的失败原因。
- 用户本人解绑第三方登录后更新当前 Session 的安全版本，当前设备保持登录；其他旧会话按现有安全规则失效。

## 10. 错误与日志边界

### 10.1 用户可见错误

API 错误响应稳定包含 `success=false`、稳定错误 `code`、用户可理解的 `message` 和 `request_id`。用户只看到正常、简洁但足够具体的错误，例如“该分组没有可用模型”或“公告图片上传失败”，并附请求 ID 供管理员排查。不得显示渠道、上游密钥、内部堆栈、数据库错误原文、目录权限细节或服务端文件绝对路径。

### 10.2 使用日志

使用日志保持现有粒度和页面结构，继续记录请求时间、用户、模型、状态、用量、额度和请求 ID 等既有字段。不给使用日志增加详细诊断字段，不新增聚合错误列表，也不把它改造成后端故障排查中心。

### 10.3 运行日志与审计日志

- 内部故障和最终失败写入现有 stdout/stderr；配置 `--log-dir` 时同时进入现有文件日志。
- 同一请求经过重试时只记录最终失败或真正异常状态，不为每次普通重试刷一条错误日志。
- 前端校验错误、预期业务拒绝和成功重试不写运行错误日志。
- 安全、账务、管理员操作和敏感读取继续写现有审计日志；不减少这些关键事件。
- `RecordErrorLog` 保持当前使用日志职责，不扩展为详细技术日志。

## 11. 首屏和全局加载性能

### 11.1 前端资源

- 开发环境启用与生产一致的路由拆包，避免单个开发 `index.js` 承载全部页面。
- `web/default/src/lib/lobe-icon.tsx` 不再使用 `import * as LobeIcons` 把整个 `@lobehub/icons` 打进首屏。改为按图标映射或按需动态加载，并缓存已加载组件。
- 未识别图标继续使用现有文字回退，不因图标加载失败阻塞页面。

目标：开发首屏传输 JavaScript 从当前约 52.7MB 降到 10MB 以下，生产首屏 gzip JavaScript 小于 1MB。

### 11.2 登录门禁

会话恢复、合规状态和来源归属状态并行预取；业务上仍按合规、来源归属、公告、正文的顺序决定展示。合规和来源归属查询失败时保持失败关闭，在 10 秒请求超时内进入可重试错误页，不能绕过门禁或永久停留在全屏 Spinner。

公告只在确认登录且前置门禁满足后检查，避免注册完成后与合规声明抢占弹窗或错误地提交确认。

生产构建不得加载 TanStack Router Devtools 或显示 `TANSTACK` 浮层。

## 12. 测试策略

所有行为修复遵循先写失败回归测试、再写最小实现的顺序。

### 12.1 后端

- IP 风险只统计达到配置阈值的共享注册、共享调用和 `401`，明确排除 `5xx`、`429` 和参数错误，并验证风险提醒不会触发自动封禁。
- rollup 列表、用户摘要、详情分页、基础设施 IP 排除和 `request_id` 跳转契约。
- 邀请码长度、随机性、枚举限流、耗尽后的再次申请、申请开关、冷却到期，以及单次提现审批和恰好一次入账。
- 公告逐条 popup、统一 Markdown/HTML 解析与净化、64 KiB 正文、图片边界、目录权限、确认幂等和未登录行为。
- 自定义/自然生成 Key 前缀、分组窄更新、普通删除墓碑、泄露指纹和泄露 Key 禁止重建。
- 兑换码创建者自领、普通/红包模式、重复领取、并发、正常 `exhausted`、`expired_pending`、一次性退款或作废及删除不重复处理资金。
- SQLite 单测以及隔离 MySQL、PostgreSQL 的迁移和事务回归。

### 12.2 前端

- Key 分组快捷修改、完整状态、自定义 Key 校验和删除后重建。

### 12.3 运行验收

1. 使用 Root、管理员和普通用户分别走完权限内的关键流程。

## 13. 实施拆分

总范围不减少，但实施计划拆成四个可独立验证的阶段：

1. IP 审计、API Key 和兑换码数据完整性。
2. 邀请奖励、公告和个人资料工作流。
3. 游乐场图片与联网搜索。
4. 首屏性能、统一 UI、翻译和最终全量回归。

每个阶段先完成定向测试和提交，再进入下一阶段；最终统一执行三种数据库、两套前端、浏览器和 Docker 验收。

## 14. 完成标准

1. 安全审计数据来源和风险结论可解释，详情可查看，用户摘要性能达标。
2. 上游普通错误不再污染安全风险；只有 API `401` 作为调用认证风险。
3. 邀请码、奖励审批、公告、游乐场、API Key、兑换码和资料流程均可从 UI 完整走通。
4. 错误提示具体但不泄露内部信息，使用日志保持原有粒度，运行日志不刷屏。
5. 首屏体积和门禁等待显著下降，失败可重试，不再出现全站永久 Spinner 或生产调试浮层。
6. 三种数据库、两套前端、浏览器和 Docker 回归全部通过，并形成可复查的测试证据。
