# CloveAPI 七类生产问题收口设计

**日期：** 2026-07-21
**状态：** 已确认，待实施
**范围：** 游乐场生图、自定义 API Key、邀请码、个人资料与第三方解绑、全局公告、安全与 IP 审计、新增功能系统设置

## 1. 背景与目标

当前源码已经恢复并具备七类能力的主要业务骨架，但实际运行仍存在界面误导、状态切换错误、会话失效、缺少服务器公告图片上传、IP 语义不清和新增能力不可配置等问题。本轮不重写现有系统，而是在既有 `Router -> Controller -> Service -> Model`、Option 配置和双前端结构上完成生产收口。

交付必须满足以下目标：

1. 页面只展示真实生效的控制项，不把协议常量伪装成可配置能力。
2. 用户状态在冷却、解绑、碰撞和跨设备确认等边界上保持一致。
3. 管理员可以在系统设置中控制新增能力的合理策略，但不能关闭必要的安全保护。
4. 公告图片由服务器安全接收、持久化并同源提供，不要求管理员准备外部图床 URL。
5. IP 审计的账号语义、IPv6 展示、后台聚合和保留策略都可解释、可运行、可测试。
6. SQLite、MySQL 和 PostgreSQL 的主数据库行为兼容；Docker 重建后公告图片和业务数据仍然存在。
7. Default 与 Classic 中存在相同功能时行为不得分叉；最终以真实浏览器和真实上游调用验收。

## 2. 非目标

- 不建设通用文件管理器、媒体素材库或对象存储控制台。
- 不持久化游乐场生成图片二进制和游乐场会话历史。
- 不根据模型名称猜测未知模型一定支持图片质量或背景参数。
- 不允许管理员配置自定义 Key 的碰撞处置、字符集或安全最小长度等安全不变量。
- 不删除或隐藏真实的 ID 1 / Root 调用记录来改善 IP 审计观感。
- 不把系统设置权限从当前 Root 范围扩大到普通管理员；权限调整若有需要应作为独立授权设计。

## 3. 已确认现状

### 3.1 游乐场生图

- 模型选择器已经按用户分组返回全部模型，符合“让用户自行选择”的既定规则。
- `输出: url` 是固定协议值，不是用户可调参数，当前展示会让用户误以为它是设置。
- 质量和背景参数只在前端能力表判定支持时发送；它们不是纯视觉控件，但仍需通过 `rightcode` 实际调用验证上游接受情况。
- 当前 `rightcode` 渠道属于 `Select` 分组，包含 `gpt-image-2`、`gpt-image-2-vip` 和 `nano-banana-2`。

### 3.2 自定义 API Key

- 后端接受完整 Key，不强制添加 `sk-`，并区分长度错误和字符错误。
- 碰撞处置会禁用旧 Key、写审计且不泄露旧 Key 所有者，安全语义正确。
- 状态显示为“已...”是徽标参与 flex 收缩并截断文字导致的纯布局问题。

### 3.3 邀请码

- 后端已经返回 `can_apply` 和 `reapply_at`。
- 前端只根据最后申请的 `rejected` 状态渲染红色拒绝态，冷却结束后仍保留过时提示。
- 重新申请冷却固定为 24 小时，用户申请功能没有运行时开关。

### 3.4 个人资料与第三方解绑

- 顶部资料头和下方资料卡重复；已有编辑弹窗，但入口位置不符合最终交互。
- 本人解绑会递增 `security_version`，却没有把新版本写回当前 Session，导致下一请求被当作旧会话拒绝。
- 昵称冷却期间不应阻止用户打开资料弹窗或修改头像。

### 3.5 全局公告

- Default 已挂载公告弹窗，但确认记录只写浏览器 `localStorage`。
- 当前管理端只能手填公共 HTTPS 图片 URL，没有服务器上传能力。
- Docker 已将 `/data` 挂载到持久卷，运行镜像工作目录也是 `/data`，可作为公告媒体持久化根目录。

### 3.6 安全与 IP 审计

- 独立 `/security-audit` 页面和投影后台任务已经存在。
- ID 1 出现在多个 IP 下是因为这些请求使用了 ID 1 所属 API Key，不是查询把 ID 1 错误拼到每一行。
- IPv6 单元格缺少可断行约束；“关联用户”也没有区分 API Key 所属账号与直接认证事件账号。
- 后台任务只支持环境变量和 ClickHouse TTL，没有跨数据库的运行时启停与通用保留天数。

### 3.7 新增功能设置

- 头像上传和昵称策略已有后端 Option，但没有管理 UI。
- 自定义 Key、邀请申请、公告弹窗/上传和 IP 审计缺少完整策略设置。
- 游乐场旧图片 Allowlist、Denylist、排序和额外允许列表已不参与当前“展示分组全部模型”流程，继续展示会构成假配置。

## 4. 总体方案

采用“纵向修复 + 集中治理设置”方案：

- 修复现有业务模块自身的状态和布局，不新建平行业务页面。
- 配置继续使用 Option 持久化，但由对应 `setting` 模块统一默认值、解析、边界和 API DTO，避免 Controller 和 Model 各自读取裸字符串。
- 公告新增一个窄用途媒体服务和一张公告确认表；不扩展成通用上传框架。
- 后台 IP 投影 Worker 保留部署级环境变量硬开关，同时在循环中读取运行时策略。
- Default 和 Classic 共享后端契约；两套前端凡存在同类控件和页面都同步行为与文案。

## 5. 游乐场生图设计

### 5.1 模型与控件

1. 模型列表继续使用当前用户分组可用模型全集，不再套用图片模型 Allowlist/Denylist。
2. 删除固定“输出 URL”展示。接口仍发送固定响应格式，但页面不把常量渲染成设置。
3. 尺寸、数量、质量、背景等控件由一个能力描述对象决定是否展示和如何构造请求。
4. 一个控件只有在请求构造器确实会把对应字段发送给上游时才允许显示。
5. 未知模型默认只显示所有图片请求都支持的基础字段，不猜测高级能力。

### 5.2 上游验证

使用 `rightcode` 的三个实际模型执行最小图片请求：

- 基线请求只包含模型和提示词。
- 对声称支持的模型分别发送非默认 `quality` 和 `background`。
- 从请求审计日志或本地可控代理确认字段真实离开 CloveAPI。
- 上游拒绝某参数时，能力表必须与实测结果一致，不能保留无效控件。

### 5.3 失败反馈

- 503、上游 4xx 和响应解析错误分别保留后端请求 ID。
- 页面显示可理解的错误摘要，不把 Axios 的 `Request failed with status code ...` 作为唯一信息。
- 失败不清空提示词、模型和用户已选择的参数。

## 6. 自定义 API Key 设计

### 6.1 可配置项

新增 `token_setting.custom_key_enabled`，默认 `true`。

- 开启：用户可在高级设置填写完整自定义 Key。
- 关闭：前端隐藏或禁用新建字段，后端拒绝携带 `custom_key` 的新建请求并返回明确错误。
- 关闭不禁用、不改写既有自定义 Key，既有 Key 继续认证。

以下规则固定，不暴露为设置：

- 长度 16–128 字符。
- 允许字符为 ASCII 字母、数字、下划线和连字符。
- 不添加、删除或规范化 `sk-`。
- 碰撞时禁用旧 Key、回滚新建、写关键审计并返回不泄露所有者的统一消息。

### 6.2 状态布局

- `StatusBadge` 的状态文字不得 `truncate`。
- Key 表格和移动卡片中的状态徽标使用稳定宽度/禁止收缩约束。
- 状态列仍允许其他长内容收缩，不能靠扩大整张表解决。

## 7. 邀请码设计

### 7.1 状态机

前端状态必须以服务端 `can_apply` 为最终依据：

- `pending`：显示待审核和撤回操作。
- `rejected && !can_apply`：显示拒绝原因和可再次申请时间。
- `rejected && can_apply`：回到普通可申请态，不继续显示旧红色拒绝主提示。
- 有活动邀请码：显示邀请码、类型、使用情况、到期时间和撤销操作。
- 已撤销、过期或耗尽且无冷却：允许重新申请。

旧拒绝记录仍保留在数据库和管理员审计中，不通过持续红色卡片占据用户主流程。

### 7.2 可配置项

扩展 `registration_setting`：

- `registration.invitation_application_enabled`：是否允许普通用户提交申请，默认 `true`。
- `registration.invitation_reapply_cooldown_seconds`：拒绝后重新申请冷却，默认 86400，允许 0 到 30 天。

管理员直接发放、审核、撤销和查看记录不受用户申请开关影响。注册是否强制邀请码继续使用已有 `registration.aff_required`，两者在同一“邀请注册”设置页展示，但语义明确分开。

### 7.3 布局

- 申请入口仍使用紧凑按钮 + 原因弹窗。
- 邀请奖励卡使用自身内容高度并与相邻区域顶部对齐，不被网格强制拉伸。
- 冷却倒计时和拒绝原因不得撑大邀请码主卡。

## 8. 个人资料与解绑设计

### 8.1 资料布局

- 删除重复的下方 `ProfileIdentityCard` 展示层。
- 顶部 `ProfileHeader` 右侧提供图标编辑按钮，点击打开现有资料编辑弹窗。
- 弹窗同时承载昵称和头像编辑，不在页面外露输入框。
- 昵称冷却期间编辑按钮保持可用；仅昵称字段不可编辑，并显示精确到日期时间的下一次可修改时间。
- 头像选择、上传到配置图床、取得 URL、提交资料的现有直传流程保留；服务器只保存经过域名策略验证的 URL。

### 8.2 本人解绑会话

本人解绑内置或自定义 OAuth 时：

1. 在事务中完成绑定删除和 `security_version` 递增。
2. 解绑成功后把新的 `security_version` 写入当前 Gin Session 并保存。
3. 当前请求者保持登录；其他旧 Session 因版本不匹配而失效。
4. 管理员对目标用户执行解绑时不更新目标 Session，目标用户所有旧会话按原规则失效。
5. 若解绑会导致账号没有任何可用登录方式，继续使用现有服务端保护并返回明确错误。

## 9. 全局公告与服务器图片设计

### 9.1 管理端交互

- 公告编辑弹窗使用文字内容区和一个方形“+”图片选择框。
- 选择后立即显示缩略图；可删除并重新选择。
- 不再向管理员暴露图片 URL 输入框。
- 保存公告前若有新文件，先上传并取得同源受管路径，再写入公告 JSON。
- 未选择图片时公告保持纯文字。

### 9.2 上传 API

新增 Root 鉴权接口：

```text
POST /api/announcement-media
Content-Type: multipart/form-data
field: file
```

响应返回相对路径：

```json
{
  "success": true,
  "data": {
    "url": "/api/announcement-media/<sha256>.<ext>"
  }
}
```

公共只读接口：

```text
GET /api/announcement-media/:filename
```

只读接口无需登录，以便游客在公告弹窗中加载图片，但文件名必须严格匹配服务生成的哈希格式。

### 9.3 文件安全与持久化

- 默认目录为当前工作目录下 `announcement-media`；Docker 工作目录是 `/data`，因此实际落盘为 `/data/announcement-media` 并随现有 `new_api_data` 卷持久化。
- 可用部署环境变量 `ANNOUNCEMENT_MEDIA_DIR` 覆盖目录，但网页系统设置不得改任意文件路径。
- 文件名由内容 SHA-256 和服务端识别的扩展名组成，忽略客户端文件名。
- 允许 PNG、JPEG、WebP 和 GIF；禁止 SVG、HTML 和未知格式。
- 同时校验上传字节上限、解码后的图片格式和像素尺寸，防止伪造 MIME 与解压炸弹。
- 写入采用临时文件 + 原子重命名；同哈希文件直接复用。
- 响应设置正确 `Content-Type`、`Content-Length`、`nosniff` 和长期不可变缓存头。
- 保存公告后，后台只清理未被当前公告引用且修改时间超过 24 小时的受管文件；不删除外部 HTTPS 图片和当前引用文件。

### 9.4 公告设置

扩展 `console_setting`：

- `announcements_enabled`：公告列表/数据是否启用，沿用现有设置。
- `announcement_popup_enabled`：是否弹出最新未确认公告，默认 `true`。
- `announcement_image_max_bytes`：单图上传上限，默认 5 MiB，允许 1–5 MiB。该范围始终低于默认 8 MiB API 请求体上限，并为 multipart 边界和字段元数据预留空间。

像素上限固定为 4096 x 4096，不暴露可削弱的无限值。

### 9.5 确认语义

新增 `announcement_acknowledgements`：

| 字段 | 说明 |
| --- | --- |
| `id` | 数据库主键 |
| `user_id` | 登录用户 ID |
| `signature` | 公告稳定签名，不保存公告正文 |
| `acknowledged_at` | 确认时间 |

约束：`user_id + signature` 唯一，并支持三种主数据库。

- 登录用户从服务端读取和写入确认，换浏览器/设备不重复弹。
- 游客继续使用本地设备存储。
- 签名覆盖公告 ID、正文、附加内容、图片路径、发布时间和类型；内容变化后视为新版本并再次弹出。
- 确认接口必须验证签名对应当前已发布公告，不能写入任意垃圾签名。

## 10. 安全与 IP 审计设计

### 10.1 展示语义

- IPv4/IPv6 单元格使用 `min-width: 0` 和可断行样式，完整 IPv6 不覆盖相邻列。
- 将含糊的“关联用户”改成“相关账号”。详情中区分：
  - API 调用事件：账号表示所用 API Key 的所有者。
  - 登录、登出和注册事件：账号表示直接执行认证行为的账号。
- 不过滤 Root/ID 1；真实高频共享 Key 使用应继续可见。
- 汇总指标补齐清晰名称，错误、登录失败和异常不能混成一个无说明数字。

### 10.2 运行时策略

新增 `ip_security_setting`：

- `ip_security.enabled`：是否采集新的 IP 安全事件并提供页面/API，默认 `true`。
- `ip_security.retention_days`：投影与事件保留天数，默认 90；`0` 表示无限，最大 3650。
- `ip_security.projection_interval_seconds`：聚合/重试间隔，默认 60，范围 5–3600。
- `ip_security.projection_batch_size`：每批数量，默认 500，范围 10–5000。

部署级 `IP_SECURITY_PROJECTION_WORKER_ENABLED=false` 始终优先，可硬关闭 Worker。环境变量配置的间隔和批大小作为启动默认/上限兼容入口；运行中 Worker 每轮读取 Option，因此管理员保存后无需重启。

### 10.3 启停与保留

- 关闭采集后不再写新的 IP 安全事件，通用业务日志和认证审计仍按原系统设置记录。
- 已有数据不在关闭瞬间删除；重新开启后继续投影。
- 保留清理对 SQLite、MySQL、PostgreSQL 都执行批量删除并重建保留窗口内 lifetime rollup。
- 使用 ClickHouse 日志源时，实际可回溯范围不得宣称超过 ClickHouse TTL；清理截止使用配置保留期与日志源 TTL 中更短的一项。
- 页面/API 在关闭时返回明确的 disabled 状态，而不是无限加载或 500。

## 11. 系统设置组织

### 11.1 站点 / 邀请注册

同一页面展示：

- 注册是否必须填写有效邀请码。
- 是否允许普通用户申请邀请码。
- 拒绝后重新申请冷却时长。

三者分别控制注册门槛、申请入口和冷却，不再把旧邀请人数限制与新审批制度混为一谈。

### 11.2 内容 / 公告

同一页面展示：

- 公告数据启停。
- 全局弹窗启停。
- 公告图片上传大小。
- 公告列表、编辑和服务器上传控件。

### 11.3 安全

新增或扩展三个分区：

- API Key：允许新建自定义 Key。
- 用户治理：头像上传开关、图床端点、允许域名、昵称最大长度和冷却时间。
- IP 审计：启停、保留天数、聚合间隔和批大小。

### 11.4 游乐场

- 保留 Tavily 降级搜索配置和真正参与运行的选项。
- 删除 Default 和 Classic 中旧图片 Allowlist、Denylist、显示排序、额外允许列表编辑器。
- 后端旧键保留读取兼容一个发布周期，但不参与模型选择；不在启动时删除用户数据库中的旧值。

## 12. API、错误和审计

- 所有新设置通过窄用途 settings DTO 校验后批量持久化，避免前端逐键保存产生半成功状态。
- 上传失败区分：未授权、缺少文件、过大、格式不支持、像素超限、目录不可写和内部写入失败。
- 公告确认失败不得关闭弹窗；成功确认后才关闭并记录已读。
- 自定义 Key 被系统关闭时使用稳定 i18n 错误，不回退为通用创建失败。
- 邀请申请被关闭或仍在冷却时返回当前策略和可重试时间。
- 本人解绑成功、公告上传/发布、公告确认、设置修改和 IP 审计敏感读取继续进入现有统一审计体系；上传审计只记录哈希、字节数和格式，不记录原文件名或文件内容。

## 13. 数据迁移与兼容

- `announcement_acknowledgements` 通过 GORM 迁移创建，唯一索引在 SQLite、MySQL 和 PostgreSQL 上使用同一语义。
- 新 Option 由设置模块提供默认值；旧数据库没有记录时不需要手工迁移。
- 头像和昵称现有键保持可读并由新的治理设置模块统一解析，避免改变已部署值。
- IP 现有事件、投影、隔离记录和 rollup 原样保留。
- 公告已有外部 HTTPS 图片继续可展示和校验；管理端新编辑流程只生成服务器受管相对路径。
- 多实例部署若要共享公告图片，必须把同一个 `ANNOUNCEMENT_MEDIA_DIR` 挂载到共享卷；单机 Docker 使用现有 `/data` 卷即可。

## 15. 验收标准

1. 游乐场不再显示“输出 URL”假设置；质量/背景均有真实请求证据。
2. 自定义 Key 状态完整显示，系统开关只影响新建，安全不变量全部保留。
3. 邀请申请冷却结束后不再显示过期拒绝主提示，布局不被奖励卡拉伸。
4. 资料编辑只从顶部卡片进入，昵称冷却说明明确，第三方自助解绑不退出当前会话。
5. 管理员可从本地选择公告图片，Docker 重启后图片仍可访问；登录用户跨设备只确认一次。
6. IPv6 不重叠，ID 1 的出现有正确账号语义，IP 审计关闭时不转圈、不 500。
7. 新增能力均在合适的系统设置页可控，旧生图假配置不再出现。
8. Go、Bun、i18n、两套前端构建、MySQL/SQLite/PostgreSQL 兼容检查、浏览器回归和 Docker 固化全部通过。
9. 最终提交只包含本轮相关源码、测试、文档和部署变更，并推送到当前私人仓库分支。
