# 订阅兑换码设计

## 目标

在保留现有余额兑换码的前提下，允许普通用户和管理员使用钱包余额购买若干份订阅，并生成一个可被多个不同用户领取的兑换码。每次领取发放一份独立、立即生效的订阅；已领取部分不可退款，未领取部分可按规则自动退款。

本功能仅在本地开发和验收，不部署到当前生产服务器，不修改 `v1.0.0-beta`，不创建 Release 或推送远端。

## 已确认规则

- 余额兑换码继续支持现有单次和红包模式。
- 订阅兑换码采用等额固定份数模式，创建者可选择购买份数。
- 创建时按 `单份钱包价格 × 份数` 一次性扣款；领取者不付费。
- 管理员与普通用户使用相同的钱包购买规则，管理员不具有免费签发入口。
- 套餐必须已启用并允许余额购买。
- 同一用户对同一个兑换码最多领取一份。
- 已有同套餐或同升级组订阅不会阻止领取；新订阅立即并行生效，独立计算额度、重置周期和有效期。
- 套餐限购针对领取者。创建待领取权益不占用创建者的个人限购次数。
- 领取者的限购次数按兑换码创建时的套餐快照计算。
- 套餐仍启用但配置发生变化时，旧兑换码继续按创建时快照发放。
- 套餐整体下架时，关联兑换码立即停止领取，并自动退还剩余份数金额。
- 创建者可在部分领取后终止兑换码；已领取订阅保持有效，只退剩余份数金额。
- 兑换码到期时自动退款，不进入管理员待结算队列。
- 已领取订阅不因兑换码到期、终止或套餐下架而失效。
- 兑换入口共用现有页面，并提供“余额 / 订阅”分段选择。后端仍校验真实类型。
- 订阅领取直接执行，不增加二次确认。

## 数据模型

### 统一兑换码主表

扩展 `UserRedemptionCode`：

- `RewardType`: `balance` 或 `subscription`。历史记录迁移为 `balance`。
- 订阅类型的 `Kind` 使用新的固定份数值 `fixed`，不进入随机金额算法。
- `MaxClaims` 表示购买总份数，`ClaimCount` 表示已领取份数。
- `TotalQuota` 表示创建时实际扣除的钱包额度。
- `ClaimedQuota` 表示已领取份数对应的已结算钱包额度。
- `RefundedQuota` 和 `ForfeitedQuota` 继续记录退款和管理员没收金额。

订阅价格可以为零，因此订阅类型的剩余份数和耗尽状态必须由 `MaxClaims - ClaimCount` 判断，不得依赖 `TotalQuota > 0`。金额关系保持为：

```text
TotalQuota = ClaimedQuota + RefundedQuota + ForfeitedQuota + RemainingPaidQuota
```

### 订阅权益快照

新增与兑换码一对一的 `UserRedemptionSubscriptionEntitlement`：

- `CodeID`，唯一索引。
- `PlanID`，用于限购统计和套餐下架关联查询。
- 套餐标题、副标题、币种和展示价格快照。
- `UnitPaidQuota`，每份实际扣除的钱包额度，作为退款的唯一金额依据。
- 订阅额度、有效期单位和值、自定义秒数。
- 额度重置周期和自定义重置秒数。
- 钱包溢出策略、升级组、降级组。
- `MaxPurchasePerUser` 限购快照。
- 创建和更新时间。

价格、权益和限购均不在领取时从当前套餐重新计算。

### 领取记录

扩展 `UserRedemptionClaim`：

- `RewardType`，历史记录迁移为 `balance`。
- `UserSubscriptionID`，订阅类型关联实际生成的订阅。
- `Quota` 对订阅类型记录该份对应的实付钱包额度，仅用于结算和审计，不充入领取者钱包。

保留 `(code_id, claimer_user_id)` 唯一约束，从数据库层保证同一码每人限领一份。

### 用户订阅重置快照

现有 `UserSubscription` 已保存额度、结束时间、用户组和钱包溢出策略，但后续重置仍读取当前套餐。为保证兑换所得订阅真正不可变，补充：

- `QuotaResetPeriod`
- `QuotaResetCustomSeconds`

新创建的订阅写入这两个字段。历史订阅字段为空时继续回退到当前套餐配置，避免迁移改变既有行为；兑换所得订阅始终使用实例快照计算后续重置。

## 创建流程

1. 接收套餐 ID、份数和有效期。
2. 校验兑换码总开关、订阅兑换码开关、份数上限和有效期范围。
3. 在事务中锁定套餐和创建者钱包。
4. 校验套餐已启用、允许余额购买且价格非负。
5. 复用现有订阅余额支付的价格换算和钱包流水规则，安全计算每份及总扣款；乘法必须检查溢出。
6. 创建兑换码及权益快照。
7. 使用稳定操作 ID 扣除总金额并写入业务审计事件。
8. 任一步失败时回滚全部写入和扣款。

创建流程不调用会立即生成个人订阅的 `PurchaseSubscriptionWithBalance`，而是复用其校验、价格换算和钱包调整基础能力。

## 领取流程

领取事务使用固定锁顺序，避免并发突破限购或与套餐下架死锁：

1. 根据兑换码的不可变关联取得套餐 ID。
2. 锁定套餐行。
3. 锁定领取者用户行，使同一用户从不同兑换码并发领取时串行化。
4. 锁定兑换码行。
5. 校验预期权益类型、兑换码状态、有效期、套餐启用状态、剩余份数及重复领取。
6. 按 `PlanID` 统计领取者已有订阅数量，并与限购快照比较。
7. 使用权益快照创建 `source=redemption` 的 `UserSubscription`。
8. 创建领取记录，增加领取份数和已结算金额；最后一份领取后转为 `exhausted`。
9. 同一事务写入一条业务审计事件。

模式选错时返回实际 `reward_type`，不创建领取记录、不消耗份数。前端切换到正确模式后由用户再次提交。

## 退款与状态机

新增 `refund_pending` 状态，用于已经封口但尚未完成钱包退款的订阅兑换码。

- 创建者取消：同步锁定兑换码并退还剩余份数金额，完成后为 `refunded`。
- 到期任务：订阅类型直接进入幂等退款；余额类型保持现有治理流程。
- 套餐下架：在套餐状态事务中将关联的 `active` 和 `disabled` 订阅兑换码批量转为 `refund_pending`，然后提交退款任务。
- 套餐重新启用不会恢复已经进入 `refund_pending` 或 `refunded` 的旧兑换码。
- 管理员临时禁用/启用不产生资金变动。
- 管理员终止继续提供明确的退款或没收选择，只处理剩余份数。

退款金额固定为：

```text
UnitPaidQuota * (MaxClaims - ClaimCount)
```

退款和没收均使用稳定操作 ID。任务重试、重复请求或服务重启不得重复入账。

套餐的完整更新接口和状态更新接口必须调用同一个状态变更服务，避免某条路由绕过兑换码封口。

## API 与页面

- 扩展现有用户兑换码创建、列表、详情和领取接口，不建立重复生命周期路由。
- 创建请求按 `reward_type` 区分余额字段和订阅字段。
- 领取请求增加 `expected_reward_type`。
- 列表支持按权益类型筛选，并返回套餐摘要、总份数、剩余份数、实付、已结算和已退款金额。
- 详情返回每次领取生成的订阅 ID。
- 创建弹窗增加“余额 / 订阅”分段选择；订阅模式显示套餐选择、份数步进器、有效期、单价和总价。
- 用户列表和管理员审计页增加权益类型及订阅内容。
- 管理员批量人工结算只包含原余额兑换码的待结算记录。
- 系统设置增加“允许创建订阅兑换码”开关；份数上限复用现有单码最大领取次数。
- 默认前端和 Classic 前端保持功能一致。

## 审计与日志

- 创建、领取、退款、没收、禁用、启用和套餐下架各写一条对应的业务审计事件。
- 钱包流水保留必要的财务记录，但不为同一状态变化生成重复业务日志。
- 领取事件记录兑换码 ID、计划 ID、领取者 ID、订阅 ID 和单份结算金额。
- 普通用户视图继续隐藏不应公开的领取者完整身份。

## 测试与验收

- 创建扣款、余额不足、禁止余额购买、免费套餐和总价溢出。
- 多份领取、同一码每人一次、最后一份耗尽。
- 同一用户并发领取不同兑换码时不会突破限购。
- 同一码并发领取不会超发。
- 套餐修改后仍按快照创建订阅并按快照重置。
- 已有并行订阅时新订阅立即生效。
- 部分领取后创建者取消只退剩余金额。
- 到期自动退款、套餐下架同步封口、异步退款重试和操作幂等。
- 套餐下架与领取竞态按锁顺序得到确定结果。
- SQLite、MySQL 和 PostgreSQL 迁移与事务行为均受测试覆盖。
- 前端覆盖创建表单总价、类型切换、列表、详情和错误状态。

## 交付边界

- 不部署生产、不迁移生产数据库、不推送远端、不发布 Release。
- 完成后在 `http://127.0.0.1:18104` 提供用户验收。
