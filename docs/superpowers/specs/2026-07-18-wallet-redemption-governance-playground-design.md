# 钱包、用户兑换码治理与游乐场最终设计

**日期：** 2026-07-18

**状态：** 已完成产品确认，待用户审阅书面规格

**范围：** 钱包中的邀请码与用户兑换码、管理员用户兑换码审计、钱包流水界面、游乐场思考控制与生图模型选择、自定义 API Key、复制交互、Default 与 Classic 双主题一致性

## 1. 文档优先级

本文记录 2026-07-18 对相关功能作出的最终决定。出现冲突时，本文覆盖以下旧设计中的对应内容：

- `docs/superpowers/specs/2026-07-13-user-governance-playground-design.md` 的自定义 API Key、用户兑换码、游乐场思考和生图模型选择部分；
- `docs/superpowers/specs/2026-07-18-runtime-governance-fixes-design.md` 的邀请码布局、用户兑换码入口、思考能力检测和生图模型筛选部分。

订阅分组限制、IP 审计等已经独立实现或已有独立规格的事项不在本文重复设计。

## 2. 目标

1. 普通用户在钱包内完成邀请码申请、邀请码管理、创建兑换码、查看自己的兑换码和兑换他人兑换码，不再在多个个人页面之间跳转。
2. 管理员通过独立的“用户兑换码”页面审计和管理所有用户创建的兑换码，但不能在该页面创建用户兑换码。
3. 用户兑换码具备可审计、可恢复、可终止、可退款或没收、可软删除的完整生命周期，所有资金变化保持事务性和幂等性。
4. 钱包不再展示流水表格；`wallet_ledger_entries` 继续作为资金记账和幂等依据，业务动作同时进入使用日志和管理员审计信息。
5. 游乐场的思考控件始终可见；关闭时即使模型仍返回思考内容，界面也必须过滤且不得保存这些内容。
6. 生图模式列出当前用户在所选分组内可用的全部模型，不再猜测哪些模型属于图片模型。
7. Default 主题补回已由后端支持的自定义 API Key，并将其放入“高级设置”。
8. Default 与 Classic 保持相同业务语义、状态、权限和本地化文案。

## 3. 非目标

- 不合并管理员创建的系统兑换码与用户使用钱包创建的兑换码数据表、资金来源或管理页面。
- 不允许普通用户查看其他用户创建的兑换码。
- 不允许管理员修改兑换码字符串、总额度、已领取记录或领取金额。
- 不删除 `wallet_ledger_entries`、钱包记账服务或现有钱包流水兼容 API。
- 不承诺“关闭思考”一定减少 Token、延迟或费用。
- 不通过模型名称、模型元数据或 endpoint type 阻止用户在生图模式选择某个模型。
- 不把完整 API Key、兑换码领取人邮箱或领取 IP 写入普通用户可见信息。

## 4. 模块边界

### 4.1 系统兑换码与用户兑换码

两类兑换码保持独立：

| 类型 | 创建者 | 资金来源 | 管理入口 | 兑换入口 |
| --- | --- | --- | --- | --- |
| 系统兑换码 | 管理员 | 系统发放额度 | 现有系统兑换码页面 | 钱包“兑换码”输入框 |
| 用户兑换码 | 普通用户或管理员为自己创建 | 创建者钱包余额 | 用户在钱包查看本人记录；管理员在“用户兑换码”审计全部记录 | 钱包“兑换码”输入框 |

钱包继续通过统一兑换服务识别两类兑换码。前端不得通过错误文案、前缀或字符串格式猜测类型。用户兑换码生成时同时检查系统兑换码表，系统兑换码创建也应检查用户兑换码表，降低跨表重码概率；若历史数据确实形成双重命中，统一兑换服务返回不泄露类型的失败结果并拒绝入账。

### 4.2 钱包记账与日志

- `wallet_ledger_entries` 是余额调整、重复请求识别和财务核对的内部事实来源。
- 使用日志是面向用户和管理员的行为记录，不替代钱包记账。
- 管理员审计信息使用现有审计 outbox 可靠投递，不允许因为日志库暂时不可用而让主事务出现“资金已变化但动作无审计”的不一致。
- 钱包流水表格仅从 Default 与 Classic 界面移除；数据库表、服务和兼容接口保留。

## 5. 钱包信息架构

### 5.1 普通用户入口

钱包标题区域提供两个紧邻的兑换码操作：

- 主按钮“新建兑换码”，打开创建侧边抽屉；
- 小型图标按钮“我的兑换码”，带 Tooltip，打开列表对话框。

钱包原有“兑换码”输入框是唯一面向普通用户的领取入口。用户兑换码列表和详情中不出现“领取”按钮。

普通用户侧边栏不再显示独立的“我的兑换码”或“用户兑换码”入口。旧的个人兑换码 URL 被普通用户访问时，重定向到钱包并通过 `show_redemptions=true` 打开“我的兑换码”对话框，避免旧书签直接失效。

### 5.2 管理员入口

- 管理员侧边栏保留独立菜单，名称固定为“用户兑换码”。
- 页面仅对 Admin 和 Root 可见，所有 Admin 均可查看和管理全部用户兑换码，不按创建者层级缩小范围。
- 页面没有创建按钮，也不复用普通用户创建流程。
- 管理员原有 `/user-redemptions` 路由继续承载该页面；普通用户不能借助手工输入路由读取管理数据。

### 5.3 钱包布局

- 邀请码改为内容高度自适应的紧凑行或紧凑面板，不再暴露常驻 Textarea。
- 邀请激励区域取消固定或被同排内容拉伸的高大布局，桌面与移动端均按内容高度排列。
- Default 与 Classic 均移除钱包流水表格。
- 页面不使用卡片嵌套卡片；邀请与兑换码操作保持扫描和重复操作所需的紧凑密度。

## 6. 邀请码交互

### 6.1 申请

- 无有效邀请码且允许申请时，只展示“申请邀请码”按钮和简短状态信息。
- 点击按钮后弹出对话框填写申请原因，原因去除首尾空格后为 5 至 500 个字符。
- 提交成功后关闭对话框并刷新状态。
- 申请原因不再常驻钱包页面，避免把邀请区域撑高。

### 6.2 待审核与撤回

- `pending` 状态显示提交时间、紧凑的申请摘要和“撤回申请”操作。
- 撤回沿用现有本人撤回接口；重复撤回收敛到同一终态，不重复记录业务结果。

### 6.3 有效邀请码

- 主区域仅保留一个复制邀请码动作，不并排展示两个含义不清的复制图标。
- 二维码仍可通过独立图标打开；注册链接复制只能在二维码对话框内作为明确命名的次级动作出现。
- 用户可以撤销自己的有效邀请码。撤销使用紧凑确认对话框并填写原因，服务端继续强制对象所有权。
- 已完成的邀请使用和奖励历史不回滚；撤销只阻止后续注册。

### 6.4 管理员操作

- 任意 Admin 或 Root 可以撤销任意用户的有效邀请码。
- 管理员发放和撤销继续使用弹窗填写原因，不在列表外侧常驻输入框。
- 管理员与用户操作均写结构化使用日志和管理员可见审计信息。

## 7. 用户兑换码创建

### 7.1 创建界面

创建使用与管理员创建系统兑换码相近的侧边抽屉结构，但只包含以下字段：

1. 模式：`单次` 或 `红包`；
2. 总额度：站点当前对外展示额度单位；
3. 领取人数：仅 `红包` 显示；
4. 有效期。

不提供名称字段、批量数量或自定义兑换码字符串。

内部类型保持兼容：`single` 对应“单次”，`random` 对应“红包”。所有中文界面、日志和提示使用“红包”，不再显示“随机包”或“拼手气随机包”。英文使用 `Red packet`。

### 7.2 额度规则

- 普通前端只提交 `amount`，其含义始终是站点展示单位。
- 后端使用 `common.QuotaFromFloatStrict(amount * common.QuotaPerUnit)` 转为整数 quota，禁止裸浮点转 `int`。
- 为兼容已有 API 客户端，`quota` 或 `total_quota` 可在未提交 `amount` 时作为原始整数 quota 使用；同一请求同时提交多个额度来源时返回参数错误。
- 单次兑换码的 `max_claims` 固定为 1。
- 红包领取人数范围为 2 至 100，总额度至少为“当前标准额度单位 × 领取人数”。
- 有效期最短 1 小时，最长 30 天，不允许永不过期。
- 创建事务先生成记录，再通过钱包服务预扣完整总额度；余额不足时整笔事务回滚。

### 7.3 用户注意事项

创建抽屉必须用紧凑提示说明：

- 创建成功会立即从钱包预留全部额度；
- 单次兑换码由第一位成功领取者获得全部剩余额度；
- 红包每个用户只能领取一次，最后一位领取者获得剩余金额；
- 到期后未领取部分自动退回钱包；
- 用户主动取消只退还尚未领取部分；管理员可依据治理决定退款或不退款；
- 兑换码属于可转发凭据，应只分享给预期领取者。

### 7.4 创建结果

- 创建成功后立即展示完整兑换码和复制动作，不要求用户先进入列表寻找。
- 复制使用共享剪贴板工具并显示明确成功或失败 Toast。
- 成功后刷新钱包余额和“我的兑换码”查询。

## 8. 用户兑换码状态与数据

### 8.1 生命周期状态

`user_redemption_codes.status` 使用以下值：

- `active`：可领取；
- `disabled`：被管理员临时禁用，不可领取，可恢复；
- `completed`：领取份数或额度全部完成；
- `cancelled`：以退款方式终止，包括创建者主动取消或管理员终止退款；
- `forfeited`：管理员无退款终止，未领取额度永久没收；
- `expired`：到期并自动退还未领取额度。

软删除不覆盖财务终态，使用独立的 `deleted_at`、`deleted_by` 和 `delete_reason` 字段表示。界面可叠加显示“已删除”，同时保留 `cancelled`、`forfeited`、`completed` 或 `expired` 等真实结算状态。

### 8.2 新增审计与结算字段

在现有字段基础上增加：

- `forfeited_quota`：已没收的未领取额度；
- `disabled_at`、`disabled_by`、`disabled_reason`；
- `terminal_actor_id`、`terminal_reason`；
- `forfeit_operation_id`：无退款终止的稳定幂等标识；
- `deleted_at`、`deleted_by`、`delete_reason`。

保留现有 `reserve_operation_id` 和 `refund_operation_id`，不重命名已有列，避免不必要的数据迁移风险。新增数值和时间字段默认 0，字符串默认空值，不重写历史记录。

### 8.3 财务不变量

对每一条兑换码始终满足：

```text
total_quota = claimed_quota + refunded_quota + forfeited_quota + remaining_quota
remaining_quota >= 0
```

其中 `remaining_quota` 由服务端计算，不依赖前端自行相减。

- `active` 和 `disabled` 可以存在正的 `remaining_quota`；
- `completed`、`cancelled`、`forfeited` 和 `expired` 的 `remaining_quota` 必须为 0；
- 退款只增加 `refunded_quota`；
- 无退款终止只增加 `forfeited_quota`，不产生钱包入账；
- 软删除不改变任何 quota 字段。

### 8.4 状态转换

| 当前状态 | 操作 | 新状态 | 资金结果 | 权限 |
| --- | --- | --- | --- | --- |
| `active` | 成功领取最后一份 | `completed` | 剩余金额全部发给最后领取者 | 已认证用户 |
| `active` | 创建者取消 | `cancelled` | 未领取部分退款 | 创建者 |
| `active` | 禁用 | `disabled` | 不变 | 任意管理员 |
| `disabled` | 恢复 | `active` | 不变 | 任意管理员 |
| `active`/`disabled` | 终止并退款 | `cancelled` | 未领取部分退款 | 任意管理员 |
| `active`/`disabled` | 终止不退款 | `forfeited` | 未领取部分记为没收 | 任意管理员 |
| `active`/`disabled` | 到期任务 | `expired` | 未领取部分自动退款 | 系统任务 |
| 任意未删除状态 | 软删除 | 原财务状态 + 已删除 | 终态不变；活动态必须同时选择退款或不退款 | 任意管理员 |

补充规则：

- 创建者不能取消 `disabled` 兑换码，防止绕过管理员冻结；只能由管理员决定后续恢复、退款终止或没收终止。
- 恢复时若已经到期，先按到期退款结算，再返回不可恢复，不允许重新激活过期兑换码。
- 对同一目标状态的重复请求返回当前结果且不重复结算、不重复写同一业务日志。
- 已进入终态后请求另一种结算方式返回状态冲突，不能把退款终态改成没收终态，反之亦然。

### 8.5 并发与幂等

- 创建、领取、禁用、恢复、终止、到期结算和软删除都在数据库事务中完成。
- MySQL 与 PostgreSQL 通过项目统一 `lockForUpdate(tx)` 锁定兑换码行；SQLite 使用兼容事务路径。
- 领取记录继续使用 `(code_id, claimer_user_id)` 唯一约束，保证每个用户每码最多领取一次。
- 钱包操作使用稳定 operation ID：预留、每位领取者入账、退款分别唯一。
- 无退款终止使用稳定 `forfeit_operation_id` 和条件更新保证重复请求不重复没收或写日志。
- 领取与管理员终止并发时，由行锁确定顺序；后执行者基于最新 `claimed_quota` 只结算真实剩余金额。
- 自动到期任务同时扫描 `active` 和 `disabled`，逐条加锁、重新检查状态与时间后结算。

## 9. 用户领取与统一钱包入口

- 钱包仍调用现有统一兑换入口，不增加第二个用户领取表单。
- 统一服务先确定系统兑换码或用户兑换码，再进入对应事务；双重命中时拒绝执行。
- 用户兑换码为 `disabled`、终态、已删除、已领取或已耗尽时均不得入账。
- 已到期的 `active` 兑换码在领取事务中先提交到期退款，再向领取者返回统一的兑换失败结果。
- 对外失败文案继续避免泄露兑换码是否存在、属于哪种类型或当前余额。
- 成功领取用户兑换码后刷新钱包余额，并记录实际领取 quota。

红包分配继续使用密码学安全随机数：除最后一人外，每人至少获得一个站点标准额度单位，同时为剩余领取人数保留最低份额；最后一人获得全部余量。

## 10. “我的兑换码”

### 10.1 列表对话框

- 从钱包小型图标按钮打开。
- 展示模式、状态、总额、已领取、剩余、份数进度、有效期和创建时间。
- 软删除记录仍作为只读历史向创建者显示，并叠加“已删除”状态，避免资金历史无故消失。
- 支持分页或增量加载，不把大量记录一次性塞入对话框。
- 每行可打开详情；`active` 状态可由创建者发起取消并退款。

### 10.2 详情

详情展示：

- 完整兑换码和可靠复制动作；
- 模式、总额度、已领取、已退款、已没收、剩余；
- 领取份数、状态、到期时间、终止时间和删除状态；
- 领取记录：脱敏领取者名称、领取额度、领取时间。

普通用户不获得领取者用户 ID、完整用户名、邮箱或 IP。用户名脱敏规则按 Unicode 字符处理：1 个字符显示 `*`；2 个字符保留首字符并追加 `*`；3 个及以上字符保留首尾字符，中间显示 `***`。

## 11. 管理员“用户兑换码”页面

### 11.1 列表与筛选

页面使用适合审计的紧凑表格，支持：

- 创建者用户 ID 或用户名；
- 模式；
- 生命周期状态；
- 是否已删除；
- 创建时间和到期时间；
- 服务端分页与真实总数。

主要列包括兑换码 ID、完整兑换码、创建者、模式、总额/已领/剩余、份数进度、状态、到期时间和创建时间。

默认列表可排除已删除记录，但提供明确的“已删除”筛选；已删除记录的详情和领取历史始终可由管理员读取。

### 11.2 管理动作

管理员可以：

- 查看详情和完整领取历史；
- 复制兑换码；
- 临时禁用 `active` 兑换码；
- 恢复未到期的 `disabled` 兑换码；
- 选择“退款”终止；
- 选择“不退款”终止，永久没收未领取额度；
- 软删除记录。

禁用、恢复、终止和删除均使用紧凑对话框收集原因。终止对话框必须明确选择“退款”或“不退款”。删除活动或禁用记录时，在同一对话框和同一事务中选择结算方式；删除终态记录时不再出现结算选择。

危险动作展示准确金额：退款对话框显示将退回多少，没收对话框显示将永久没收多少。不得只显示笼统确认文案。

### 11.3 管理员详情

管理员查看的领取记录包含：

- 领取记录 ID；
- 完整领取者用户 ID；
- 完整用户名；
- 领取额度；
- 领取时间。

管理员详情同样不展示领取者邮箱或 IP，因为这些信息不属于兑换码治理所需最小数据集。

## 12. API 与服务接口

### 12.1 保留接口

- `POST /api/user-redemption/`：创建本人用户兑换码；
- `GET /api/user-redemption/`：列出本人兑换码；
- `GET /api/user-redemption/:id`：读取本人详情；
- `POST /api/user-redemption/:id/cancel`：创建者取消并退还未领取部分；
- `POST /api/user-redemption/claim`：保留兼容，但普通前端不再直接使用；
- `GET /api/user-redemption/admin/`：管理员列表；
- `GET /api/user-redemption/admin/:id`：管理员详情；
- `POST /api/user-redemption/admin/:id/cancel`：保留为旧版“终止并退款”兼容入口。

### 12.2 新增管理员接口

- `POST /api/user-redemption/admin/:id/disable`，请求体 `{ "reason": string }`；
- `POST /api/user-redemption/admin/:id/enable`，请求体 `{ "reason": string }`；
- `POST /api/user-redemption/admin/:id/terminate`，请求体 `{ "settlement": "refund" | "forfeit", "reason": string }`；
- `POST /api/user-redemption/admin/:id/delete`，请求体 `{ "settlement"?: "refund" | "forfeit", "reason": string }`。

删除活动或禁用兑换码时 `settlement` 必填；删除终态兑换码时省略该字段。所有接口继续在 Service 层校验权限和状态，不能依赖路由中间件或前端隐藏。

### 12.3 DTO

列表和详情不直接序列化 GORM 模型，使用明确 DTO，至少提供：

- `remaining_quota` 服务端派生值；
- `deleted` 与删除时间；
- 创建者摘要；
- 按查看者权限生成的领取记录视图。

用户 DTO 只含脱敏领取者名称；管理员 DTO 才包含领取者 ID 和完整用户名。

## 13. 使用日志与管理员审计

以下动作全部记录：

- 创建；
- 领取；
- 创建者取消；
- 管理员禁用；
- 管理员恢复；
- 管理员终止并退款；
- 管理员终止不退款；
- 自动到期退款；
- 软删除。

使用稳定 action：

```text
user.redemption.create
user.redemption.claim
user.redemption.cancel
user.redemption.disable
user.redemption.enable
user.redemption.terminate_refund
user.redemption.terminate_forfeit
user.redemption.expire_refund
user.redemption.delete
```

现有旧 action 在前端显示层映射到对应新文案，历史日志不迁移。

审计 outbox 增加独立的日志归属用户能力，例如 `AuditEvent.LogUserID`：真实操作者继续保存在 `ActorID`，日志可归属受影响用户，避免为了让用户看见记录而伪造操作者。未指定时保持 `LogUserID = ActorID` 的兼容行为。

普通用户可见 `other.op` 中的脱敏参数，包括兑换码 ID、动作、自己的金额变化和结果；`admin_info` 与 `audit_info` 继续由日志查询层剥离。管理员查看全局日志时可以看到真实操作者、创建者、领取者、兑换码 ID、金额、结算方式、原因、请求 ID 和结果。

不在日志中写入完整兑换码、完整 API Key、邮箱、Authorization、Cookie 或领取 IP。完整兑换码只存在受权限保护的兑换码详情 API。

## 14. 游乐场思考控制

### 14.1 控件语义

- 思考控件在聊天模式始终显示，选项固定为“关闭 / 低 / 中 / 高”。
- 不再根据模型名隐藏或禁用控件。
- 选择值应用于之后发起的请求。
- Tooltip 明确说明：关闭会隐藏游乐场中的思考内容，并尝试要求模型停止思考，但不保证减少 Token、延迟或费用。

### 14.2 请求端最佳努力

- 前端对四个选项始终发送规范值：`off` 映射为 `none`，其余发送 `low`、`medium`、`high`。
- 后端只校验值集合，不因模型或渠道不支持而返回 400。
- 已知支持的适配器继续映射为对应厂商字段。
- 已知不支持或无法可靠表达的路由清除该字段并继续请求，相当于忽略用户调节。
- 不把前端模型名猜测当作协议能力事实。
- 日志只记录实际向上游应用的思考档位；被忽略时记录 `reasoning_control_ignored=true`，不能伪装为成功关闭。

### 14.3 “关闭”时的内容过滤

关闭思考时，前端必须同时处理两种返回形式：

1. 独立的 `reasoning_content` 或 `reasoning` 字段；
2. 普通内容中的 `<think>...</think>` 标签。

行为要求：

- 流式 `reasoning_content` 直接丢弃，不写入消息状态、调试状态或浏览器持久化存储；
- 非流式响应忽略 reasoning 字段；
- 对普通内容使用有状态过滤器移除 `<think>` 区间，必须正确处理标签被拆到多个 SSE chunk 的情况；
- 未闭合的 `<think>` 从开始标签到响应结束全部丢弃；
- 标签外的正常文本保持原顺序；
- 关闭模式下最终消息对象不包含 reasoning 数据，保存会话时也不能重新带回；
- 若过滤后模型没有可显示内容，结束加载并显示“模型未返回可显示内容”，不能无限等待。

低、中、高仍沿用现有思考面板展示独立 reasoning 或 `<think>` 内容。

## 15. 游乐场生图模型

- 生图模式的模型列表直接复用当前用户在所选分组可用的完整模型列表。
- 分组仍通过 `GetUserUsableGroups` 校验；用户不能查询或使用未授权分组。
- 请求模型列表时不传 `endpoint_type=image-generation`，也不调用名称匹配或 endpoint 元数据筛选。
- 现有 `PlaygroundImageModelsAllowlist`、`Denylist`、`DisplayOrder` 和 `ExtraAllowlist` 不再影响生图选择器；设置页面移除这些无效控件，后端暂时保留旧 option key 以兼容已有配置数据。
- 选中非图片模型后，调用仍走 `/pg/images/generations`；上游或网关返回的正常错误由生图面板明确展示。
- 无模型时提示“当前分组没有可用模型”，而不是错误声称“没有图片模型”。
- 模型名推断可继续用于渐进展示质量、风格、背景等可选字段，但不得用于决定模型是否可选择；未知模型只显示基础字段。

## 16. 自定义 API Key

### 16.1 Default 主题

在现有“新建 API Key”侧边抽屉的“高级设置”折叠区增加“自定义 API Key（可选）”字段：

- 仅创建时显示；编辑已有 Key 时不显示；
- 仅 `tokenCount = 1` 时显示；批量创建时隐藏并从 payload 中强制省略；
- 从单个切换到批量时清空隐藏字段，防止旧值残留提交；
- 留空时沿用系统自动生成；
- 长度 16 至 128，只允许 ASCII 字母、数字、`_` 和 `-`；
- 字段说明不得暗示可以在创建后修改完整 Key。

前端校验只用于即时反馈，后端 `controller/token.go` 的格式校验、碰撞检测、疑似泄露隔离和审计继续作为最终边界。碰撞失败继续返回统一的“自定义 API Key 不可用”文案，不泄露已有 Key 信息。

### 16.2 Classic 主题

Classic 保留已有创建能力，并将等价字段归入“高级设置”区域；同样只在创建单个 Key 时显示和提交。两套主题共享相同校验规则和后端语义。

## 17. 复制行为

Default 以现有 `web/default/src/lib/copy-to-clipboard.ts` 为唯一剪贴板实现，Classic 以现有公共 `copy()` helper 为入口。目标功能中不得直接调用 `navigator.clipboard.writeText`。

统一顺序：

1. 优先调用 `navigator.clipboard.writeText`；
2. 不可用或失败时创建临时 textarea 并调用兼容复制命令；
3. 返回明确布尔结果；
4. 调用方显示成功或失败 Toast。

本次覆盖邀请码、用户兑换码、管理员用户兑换码、生图 URL 和自定义 Key 相关复制入口。按钮必须有可访问名称或 Tooltip。

## 18. 国际化与双主题一致性

- 所有新增和修改的用户可见文本必须进入 Default 与 Classic 的现有 i18n 体系。
- Default 更新 `en`、`zh`、`fr`、`ru`、`ja`、`vi`；Classic 更新项目当前维护的对应 locale。
- 关键术语固定：管理员菜单“用户兑换码”，用户弹窗“我的兑换码”，创建模式“单次 / 红包”，终止方式“退款 / 不退款”。
- 两个主题允许使用各自组件库，但必须具有相同字段、状态、权限、错误和确认语义。
- 所有图标按钮提供 Tooltip 和 `aria-label`；对话框打开后焦点进入第一个可操作字段，关闭后返回触发按钮。

## 19. 测试策略

所有行为变更遵循 TDD：先写能复现当前缺陷的失败测试，再写最小实现。

### 19.1 Go 单元与集成测试

- 创建额度单位转换、歧义额度来源拒绝、红包最低额度和有效期边界；

- 游乐场合法档位、未知能力忽略而非失败、实际应用档位日志；
- 生图模型接口仍强制用户分组权限。

数据库行为先在 SQLite 测试；行锁、事务、唯一约束和幂等结算在本地 MySQL QA 容器增加集成验证。所有迁移和查询必须兼容 PostgreSQL。

## 20. 验收标准

- 普通用户无需离开钱包即可完成邀请码和用户兑换码全部常用流程。
- 管理员“用户兑换码”可审计所有用户记录且没有创建入口。
- 禁用可恢复；退款终止和没收终止金额正确；软删除不丢失详情、领取记录或日志。
- 所有资金变化只有一次钱包记账，重复操作不重复扣款、入账、退款或没收。
- 钱包不再展示流水表格，但相关业务动作能在使用日志中查询。
- 创建者看到脱敏领取者，管理员看到完整 ID 和用户名，双方都看不到不必要的邮箱和 IP。
- 思考控件不再因模型名禁用；关闭后界面和持久化消息均没有 reasoning 或 `<think>` 内容。
- 生图模式展示当前用户和分组可用的全部模型，不再出现因图片模型识别失败而无法选择的情况。
- Default 的自定义 API Key 在高级设置中可见，仅单个新建时生效；Classic 语义一致。
- 兑换码、邀请码、生图 URL 等相关复制按钮在安全上下文和 fallback 环境都有明确成功或失败反馈。
