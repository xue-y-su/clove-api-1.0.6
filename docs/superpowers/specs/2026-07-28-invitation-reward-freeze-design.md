# 邀请奖励冻结与审批历史设计

## 目标

管理员可以长期查看邀请奖励提现审批历史，并在误批或确认存在刷邀请行为后，
冻结已经到账的整笔奖励。冻结时全额冲正用户钱包，余额不足允许变成负数；
解除冻结时原额恢复。所有审批、冻结与解除动作都必须可追溯。

## 状态与账务

- 提现申请保持 `pending`、`paid`、`rejected`，新增 `frozen`。
- 只有 `paid` 申请可以冻结，只有 `frozen` 申请可以解除冻结。
- 冻结使用独立的负向钱包流水，类别为 `invitation_reward_freeze`。
- 冻结允许余额小于零，不改变其他钱包扣款的余额不足保护。
- 解除冻结使用独立的正向钱包流水，类别为 `invitation_reward_unfreeze`。
- 每次冻结生成递增修订号；同一修订号的冻结和解除操作分别幂等。
- 奖励明细状态随申请在 `paid` 和 `frozen` 之间切换。
- 用户奖励汇总单独返回冻结金额，冻结金额不计入已到账金额。

## 历史与详情

- 审批页拆分为“待审批”和“审批历史”，默认进入待审批。
- 审批历史包含 `paid`、`rejected`、`frozen`，不会因默认筛选而消失。
- 申请详情返回：申请人、额度、奖励明细、来源账号、注册 IP、审批人、
  审批说明、钱包操作 ID，以及冻结/解除历史。
- 每次冻结或解除写独立动作记录和审计事件，保留操作人、原因、金额、时间、
  修订号及钱包操作 ID。
- 冻结和解除都要求填写原因并二次确认。

## 权限与并发

- 沿用邀请奖励审批现有管理员层级规则。
- 服务层在事务内锁定管理员、目标用户、申请、申请明细和奖励记录。
- 状态条件更新保证并发请求只成功一次；账本 `operation_id` 提供重试幂等。
- 用户余额、申请状态、奖励状态、动作历史和审计 Outbox 在同一事务提交。

## 双前端与响应式

- Default 和 Classic 都提供待审批/审批历史分区、详情、冻结和解除入口。
- 桌面保留可扫描表格；小于平板宽度使用卡片列表，不依赖横向拖动才能操作。
- 长用户名、操作 ID、原因和来源信息允许换行，不挤压状态与操作按钮。
- 分页在窄屏隐藏非必要总计并允许按钮换行，保证 320px 宽度完整可操作。
- 同一轮修复共用分页、API Key 分组浮层、Playground 发送区和渠道工具栏的
  已复现溢出，但不改动已经正常的数值展示。

## 测试与验收

1. SQLite 与 MySQL 验证审批、冻结成负余额、幂等重试、解除恢复和并发互斥。
2. API 测试验证权限、错误码、详情来源与动作历史。
3. Default/Classic 行为测试验证历史常驻、移动卡片和冻结操作。
4. 真实浏览器覆盖 320x568、390x844、768x1024 和桌面宽度。
5. 冻结后用户余额为负并停止正常付费调用；充值或新奖励先抵扣负余额。
6. 解除冻结后余额精确恢复，审批和动作历史仍完整保留。
