# 邀请交易返佣设计

## 目标

把现有注册邀请奖励、被邀请人赠送、充值返佣和官方兑换码返佣整理为一套可配置、可审计的邀请激励体系。注册仍建立稳定的直接邀请关系；奖励既可保留原有的“注册即产生固定奖励”，也可由被邀请人的真实现金支付或官方兑换行为触发。所有邀请人奖励继续经过用户提交和管理员审批后才进入钱包。

本功能与订阅兑换码、邀请海报和模型广场功能一起仅在本地开发和验收。不得部署当前生产服务器、修改 `v1.0.0-beta`、推送远端或创建 Release。

## 术语

- **邀请人**：用户注册时通过有效邀请码绑定的直接上级用户。
- **被邀请人**：通过邀请码完成注册的用户。
- **注册固定奖励**：被邀请人注册成功后，为邀请人生成的固定额度奖励。
- **注册赠送**：被邀请人注册成功后，直接进入其钱包的固定欢迎额度。
- **交易返佣**：被邀请人完成合格现金支付或官方兑换后，按比例为邀请人生成的奖励。
- **官方兑换码**：由管理员入口正式发行并在创建时固化官方发行标记的兑换码。
- **奖励事实**：一笔注册奖励或交易返佣的不可重复业务记录。

只支持直接邀请关系，不做多级分佣，不允许注册后更换邀请人。来源归属关系不等同于邀请码关系，不产生邀请奖励或返佣。

## 统一设置

系统设置新增独立的“邀请激励”分区，Default 和 Classic 前端使用同一组后端配置：

- `enabled`：邀请激励总开关，默认开启。
- `inviter_registration_reward_enabled`：邀请人注册固定奖励开关，默认开启。
- `invitee_registration_gift_enabled`：被邀请人注册赠送开关，默认开启。
- `cash_commission_enabled`：现金支付返佣开关，升级时默认关闭。
- `cash_commission_rate`：现金支付返佣比例，升级时默认 `0.00`。
- `admin_balance_redemption_commission_enabled`：管理员余额兑换码返佣开关，升级时默认关闭。
- `admin_balance_redemption_commission_rate`：管理员余额兑换码返佣比例，升级时默认 `0.00`。
- `admin_subscription_redemption_commission_enabled`：管理员订阅兑换码返佣开关，升级时默认关闭。
- `admin_subscription_redemption_commission_rate`：管理员订阅兑换码返佣比例，升级时默认 `0.00`。

邀请人注册固定奖励和被邀请人注册赠送继续使用现有额度配置。原设置键保持兼容，但两项金额从通用额度设置页面移动到“邀请激励”分区。

关闭总开关时仍记录邀请关系、邀请码使用记录和邀请人数，但不生成任何新奖励。子开关关闭后保留其金额或比例，重新开启无需重填。设置变化只影响变化后发生的新事件，不追溯修改历史奖励。

比例允许为 `0` 或任意大于 `0` 的值，包括超过 `100%` 的比例，支持两位小数，不设置业务上限。后端以万分比整数保存比例快照，例如 `5.25%` 保存为 `525`，计算时使用整数或精确十进制运算。设置接口只拒绝负数、超过两位小数、无效数字以及超出钱包整数可表示范围的技术性溢出值。

## 合格来源

### 注册固定奖励

总开关和邀请人固定奖励开关均开启、固定金额大于零且存在有效邀请码关系时，注册成功生成一条邀请人奖励事实。该奖励立即可供邀请人提交提现，但不会直接进入钱包。

总开关和被邀请人赠送开关均开启、固定金额大于零时，注册赠送在注册事务中直接记入被邀请人钱包。邀请关系和赠送使用稳定操作编号，重试不得重复入账。

### 现金支付

以下两类交易共用现金支付返佣开关和比例：

1. 钱包在线充值成功。
2. 通过 Stripe、易支付、Creem、Waffo、Waffo Pancake 等现金通道直接购买订阅成功。

钱包余额购买订阅不返佣，因为余额充值已经可能产生一次返佣。管理员补单只有在它完成一笔已验证的原始现金订单时才沿用该订单来源；直接调整余额、赠送额度、签到奖励、邀请奖励提现、退款补偿和其他内部钱包入账均不返佣。

现金返佣基数是支付通道确认的实际支付金额换算出的内部额度，不是钱包最终到账额度。充值折扣、充值赠送和套餐附赠额度不进入基数。支付通道能返回最终结算金额时以签名验证后的结算金额为准；否则使用创建订单时固化的应付金额快照。

订单保存原始支付金额、币种和换算后的 `EligibleQuota`。返佣金额为：

```text
CommissionQuota = floor(EligibleQuota * RateBasisPoints / 10000)
```

### 管理员余额兑换码

只有管理员管理入口创建的传统余额兑换码参与返佣。每次成功兑换后，以实际兑换面值作为 `EligibleQuota`，使用管理员余额兑换码返佣比例生成奖励。

用户使用钱包创建的单次、红包或其他余额兑换码始终不返佣，即使创建者后来被提升为管理员。

### 管理员订阅兑换码

只有创建时被后端标记为官方管理员发行的订阅兑换码参与返佣。每成功领取一份订阅，以兑换码权益快照中的 `UnitPaidQuota` 作为 `EligibleQuota`，使用领取时的管理员订阅兑换码返佣比例生成奖励。

一张多人、多份兑换码按每条成功领取记录分别生成奖励。同一用户重复领取、领取失败、超过限购或未实际创建订阅时不生成奖励。用户购买创建的订阅兑换码始终不返佣。

官方发行资格在兑换码创建时固化，不根据领取时创建者的当前角色推断。管理员后来降权不改变已正式发行的兑换码；普通用户后来升权也不会使其旧兑换码获得资格。套餐价格、额度或状态后续变化不改变兑换码内的单份价值快照。

## 奖励数据模型

现有 `InviteRewardPayout` 从“每次邀请码使用只有一条邀请人奖励”扩展为通用奖励事实，并继续被提现申请、审批和冻结流程引用。新增或调整字段：

- `InviteCodeUseID`：关联原始邀请码使用记录。
- `TriggerType`：`registration_inviter`、`cash_topup`、`cash_subscription`、`admin_balance_redemption` 或 `admin_subscription_redemption`。
- `TriggerID`：支付订单号、兑换记录 ID、订阅订单号或订阅领取记录 ID。
- `EligibleQuota`：计算返佣的内部额度基数。
- `RateBasisPoints`：事件发生时的比例快照；注册固定奖励为零。
- `Amount`：原始奖励额度，使用 64 位整数。
- `ReversedAmount`：累计撤销额度。
- `ReversalState`：`none`、`partial` 或 `full`。
- `CreatedAt`、`UpdatedAt`：奖励事实时间。

数据库唯一约束改为 `(trigger_type, trigger_id, recipient_kind)`。历史记录根据原邀请码使用记录和收款角色回填注册奖励来源，原金额、状态、审批记录与钱包流水保持不变。旧的 `(invite_code_use_id, recipient_kind)` 唯一约束在回填和新约束建立后移除，使同一被邀请人的多次真实交易可以分别产生奖励。

新增不可变的 `InviteRewardReversal`：

- 奖励 ID、退款来源类型和退款来源 ID。
- 本次退款基数、本次撤销奖励额度及累计撤销额度。
- 撤销前奖励状态、钱包冲正操作编号、发生时间。
- 唯一约束 `(reward_id, refund_source_type, refund_source_id)`。

提现申请保留提交时的原始 `Amount`，接口同时返回聚合的 `ReversedAmount` 和 `NetAmount`。提现申请项目不物理删除，管理员始终能看到某条奖励为何被排除或冲回。

## 原子性与幂等

奖励生成必须和对应的充值到账、订阅激活或兑换成功处于同一个数据库事务。处理顺序为：

1. 锁定来源订单或领取记录。
2. 锁定被邀请人及其邀请码使用关系。
3. 校验总开关、来源子开关和来源资格。
4. 读取并固化当前比例，精确计算奖励。
5. 使用来源唯一键创建奖励事实和业务审计 Outbox。
6. 完成来源状态变化并提交事务。

无邀请人、非邀请码来源、开关关闭、比例为零或来源不合格属于正常跳过，不写奖励、使用日志或告警。数据库异常回滚完整事务，由原支付或兑换幂等机制重试。重复支付回调、重复兑换请求和并发领取命中同一来源唯一键时只返回既有结果，不重复生成奖励。

支付和订阅完成路径调用同一个返佣入口，不允许各支付提供商复制计算规则。传统管理员兑换码和订阅兑换码领取也调用该入口，但分别传入明确的来源类型和价值快照。

## 提现、审批与冻结

新交易返佣沿用现有奖励提现流程：

- 奖励生成后立即为可提现状态，不设置等待期。
- 邀请人可以把当前全部可提现净额提交为一笔提现申请。
- 管理员在详情中查看来源后批准或拒绝。
- 只有批准才通过钱包账本进入邀请人余额。
- 已到账申请继续支持整笔冻结和解除冻结。

提交和审批时按奖励的 `Amount - ReversedAmount` 计算净额，并在事务中重新校验。并发退款、提交和审批使用固定锁顺序：目标用户、提现申请、申请项目、奖励事实、退款记录。状态条件更新与钱包稳定操作编号共同保证只执行一次。

## 退款与冲正

现金充值或现金订阅订单发生全额或部分退款、拒付时，按原始比例和退款基数精确撤销对应返佣。累计撤销不得超过原始奖励金额。

- **可提现**：增加 `ReversedAmount`；全额撤销后不再允许提交。
- **已提交待审批**：保留申请项目，重新计算申请净额；全部项目净额为零时把申请标记为系统取消。
- **已审批到账**：使用稳定操作编号写负向钱包流水；余额不足允许变成负数。
- **已冻结**：不再次扣款，只减少后续可解除冻结的净额；解除冻结不得恢复已撤销部分。

提现申请保留原始金额、累计撤销金额和净额。整笔冻结只冻结尚未撤销的已到账净额，解除冻结也只恢复当前未撤销净额，避免退款与冻结重复扣款或重复恢复。

官方管理员兑换码一旦成功兑换，不随兑换码剩余份数退款而自动撤销已领取部分的返佣。异常官方兑换通过现有管理员拒绝、冻结和解除流程处理。

退款处理入口接受稳定的退款来源 ID；相同退款通知重复到达时返回已有撤销记录。当前支付通道已支持的退款或拒付通知接入该入口，后台人工订单退款也必须调用同一入口。

## 使用日志与审计

用户可见使用日志只记录实际奖励或钱包状态变化：

- 返佣生成：邀请人一条简洁日志，例如“邀请充值返现 +9.00，比例 10%”。
- 注册固定奖励：邀请人一条“邀请注册奖励 +X”。
- 提现审批到账：复用现有钱包入账日志，不额外重复记录。
- 退款撤销：邀请人一条“邀请返现撤销 -9.00”。
- 冻结和解除：复用现有冻结日志，不重复记录奖励状态变化。

被邀请人的充值、兑换和订阅日志保持原样，不因产生返佣再增加第二条。开关关闭、比例为零、没有邀请人、用户兑换码、资格校验、失败尝试和重复回调均不写使用日志。

普通使用日志只显示来源大类、金额和比例，不显示完整订单号、兑换码或内部计算载荷。完整来源编号、被邀请人、支付/兑换价值、比例快照、奖励金额、退款和冲正操作编号写入奖励详情及管理员审计。日志由带唯一事件编号的事务 Outbox 提交，重试不会形成噪声。

## API 与界面

### 系统设置

Default 和 Classic 的系统设置都提供统一“邀请激励”分区。总开关关闭时禁用子控件但保留值；每个返佣来源使用独立开关和比例输入。比例输入允许超过 `100%`，步进为 `0.01`，不设置前端最大值。

### 用户钱包

现有“邀请返现”卡片继续显示邀请人数、可提现、审批中、已到账和已冻结等汇总。只有总开关与现金返佣开关均开启且比例大于零时，卡片额外显示一行：

```text
充值返现 X%
```

现金返佣关闭或比例为零时整行隐藏。卡片不展示管理员余额码、管理员订阅码比例或其他关闭状态，避免信息过密。卡片展示当前现金比例；历史奖励详情展示事件发生时的比例快照。

### 管理员审批

提现详情增加来源类型、被邀请人、实际支付或兑换价值、比例快照、原始奖励、已撤销金额、净额和退款状态。列表保持紧凑，不直接铺开完整长编号；详情中提供完整编号和复制操作。桌面使用可扫描表格，移动端使用卡片列表，长编号允许换行且不挤压状态和操作按钮。

普通用户接口不返回其他用户的完整身份、完整兑换码或支付提供商载荷。

## 迁移与兼容

- 历史注册奖励按原金额和状态保留，不重新计算。
- 历史已支付、冻结、拒绝和待审批申请保持原生命周期。
- 原邀请人和被邀请人固定金额配置继续生效；新增两个开关默认开启，保持升级前注册行为。
- 新交易返佣开关默认关闭且比例为零，避免升级后未经管理员配置即产生新财务义务。
- 迁移覆盖 SQLite、MySQL 和 PostgreSQL；先回填来源，再建立新唯一索引，最后移除旧唯一索引。
- 数据迁移和服务启动可重复执行，不重复创建奖励、退款或钱包流水。

## 测试与验收

### 后端

- 总开关、五个子项、旧金额键兼容和配置往返。
- `0%`、`5.25%`、`200%`、`1250.75%`、负数、精度超限和技术性溢出。
- 注册固定奖励和被邀请人赠送可分别启停，邀请关系与邀请人数始终保留。
- 钱包充值按实际支付金额而不是到账额度返佣。
- 现金订阅购买返佣，余额订阅购买不返佣。
- 管理员余额码和管理员订阅码返佣，用户创建的两类兑换码不返佣。
- 官方发行标记在管理员降权和普通用户升权后仍保持创建时语义。
- 多份、多用户领取，同一用户重复领取和并发领取。
- 支付回调、兑换请求和奖励 Outbox 重试只生成一条奖励与一条使用日志。
- 部分退款和全额退款在可提现、待审批、已到账和已冻结状态下的净额、冲正与解除冻结结果。
- 历史奖励迁移后金额、状态、审批项目和钱包操作不变。
- SQLite 单元/并发测试，以及 MySQL、PostgreSQL 迁移和事务集成测试。

### 前端与浏览器

- Default 和 Classic 的统一设置区保存、禁用状态、超 `100%` 比例和旧值迁移。
- 钱包卡片只在现金返佣有效时显示一行当前比例。
- 管理员详情展示完整计算证据，列表不被长编号撑破。
- 桌面、平板及 320px/390px 移动视口无重叠、横向穿版或不可操作控件。
- 使用保留的本地数据库启动 `http://127.0.0.1:18104`，不删除卷、不重建数据，完成 Go、两套前端和真实浏览器回归。
