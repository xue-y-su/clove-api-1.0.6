# 操练场附件与邀请人数限制设计

## 目标

把默认前端操练场里目前仍是占位状态的附件入口完善到可用状态，同时新增邀请人数限制，避免普通用户通过邀请注册无限扩散。这个限制只约束成功注册，不影响管理员运营动作，也不影响来源归因流程。

## 当前现状

默认前端操练场已经有附件菜单入口，但点击后只提示“功能开发中”。它的消息和请求类型已经支持 OpenAI 兼容的多模态内容结构，也就是 `text` 和 `image_url`，所以图片支持可以先在前端完成，不需要改 relay API。后端操练场请求走 `/pg/chat/completions`，复用普通聊天补全 relay。

classic 操练场已经支持图片 URL 输入和粘贴图片。当前主要缺口在默认前端。

邀请注册已经支持必填 `aff` 邀请码。用户表里已有 `aff_code`、`aff_count`、`aff_quota`、`aff_history_quota` 和 `inviter_id`。其中 `aff_count` 更偏奖励统计，而且会受邀请奖励配置影响，所以不能作为邀请限制的判断依据。真正的成功邀请人数应该按 `inviter_id` 指向该邀请人的用户数量统计。

## 设计决策

### 操练场附件

默认前端先实现本地附件能力：

- 支持在操练场输入框选择图片文件。
- 支持从剪贴板粘贴图片。
- 图片在浏览器端转换为 `data:image/...;base64,...`。
- 发送包含图片的消息时，构造 OpenAI 兼容的 content array：一个文本 part，加上每张图片一个 `image_url` part。
- 已选择图片在输入区附近显示为紧凑附件条目，包含文件名、大小、缩略图和移除按钮。
- 支持选择文本文件。
- 文本文件在浏览器端读取后，作为清晰分隔的“附件上下文”拼入用户消息正文。
- 文本文件支持范围保持克制：`.txt`、`.md`、`.json`、`.csv`、`.tsv`、`.log`、`.yaml`、`.yml`、`.xml` 和 `text/*`。
- PDF、Word、Excel、压缩包等二进制文件本轮不做解析。用户选择时给出明确提示，避免表现成“上传成功但模型其实读不了”。

限制规则：

- 图片限制数量和单张大小。
- 文本文件限制数量、单文件大小和合计文本长度。
- UI 状态只保存轻量附件元信息，避免把大量 base64 内容长期存进 localStorage 的会话历史里。

后期扩展余地：

- 把附件统一抽象为本地 `PlaygroundAttachment`。当前它们会被转换成 data URL 或内联文本；以后官方 Files API 可用后，同一套 UI 可以改成先上传到后端，再把附件转换为 file ID 或托管 URL，不需要重做用户交互。

### 邀请人数限制

新增“成功注册邀请人数上限”。这个限制只管注册，不管来源归因。

规则：

- 密码注册、OAuth 注册、后台创建用户时，如果使用了邀请码，都需要检查邀请上限。
- 来源归因忽略邀请上限。来源归因选项指向某个用户时，即使该目标用户已达到注册邀请上限，也仍然允许绑定 `inviter_id`。
- 如果邀请码所属用户是管理员或超级管理员，邀请限制不生效。
- 如果邀请码所属用户是普通用户，则比较该用户的成功邀请人数和有效上限。
- 成功邀请人数按 `COUNT(users.id WHERE users.inviter_id = 邀请人ID)` 统计。
- 默认情况下，已删除用户仍然计入成功邀请人数。这个限制防的是历史注册扩散，而不是只看当前活跃用户数量。

上限表达方式：

- 数字永远表示真实人数。`0` 就是可以邀请 `0` 人，也就是不允许普通用户继续邀请。
- “不限制”必须用独立布尔开关表达，不能用 `0` 表达。
- 系统设置：
  - `registration.invite_limit_unlimited`：默认 `true`，保证升级后老站点不会突然卡住注册。
  - `registration.invite_limit_count`：整数，默认 `0`。
- 用户级覆盖：
  - `invite_limit_mode`：`inherit`、`limited` 或 `unlimited`。
  - `invite_limit_count`：仅当 mode 为 `limited` 时使用。

有效上限计算：

- 邀请人是管理员或超级管理员：无限制。
- 普通用户覆盖为 `unlimited`：无限制。
- 普通用户覆盖为 `limited`：使用该用户自己的 `invite_limit_count`。
- 普通用户覆盖为 `inherit`：使用系统设置。
- 系统 `invite_limit_unlimited = true`：无限制。
- 系统 `invite_limit_unlimited = false`：使用 `registration.invite_limit_count`。

当普通邀请人已经达到上限时，注册应在创建用户前失败，并返回明确错误，例如“该邀请码已达到邀请人数上限”。

## UI 变化

### 系统设置

在“邀请注册”设置里：

- 保留现有“注册必须填写邀请码”开关。
- 新增默认邀请人数上限数字输入。
- 在数字输入旁边新增一个紧凑的“不限制”按钮或开关。
- 开启“不限制”时，数字输入禁用。
- 关闭“不限制”时，严格按数字限制。
- 文案必须明确：`0` 表示不能邀请任何人。

### 成员管理

在成员编辑抽屉里：

- 新增“邀请限制”区域。
- 显示该用户当前成功邀请人数。
- 管理员可以选择：
  - 跟随系统设置。
  - 自定义上限，并填写数字。
  - 该用户不限制。
- 管理员和超级管理员仍可展示这些字段，但需要提示他们作为邀请人时本身免限。

### 钱包

在钱包邀请奖励卡片里：

- 显示成功邀请人数、有效上限和剩余名额。
- 不限制时显示“不限制”或 `Unlimited`，不显示伪造的数字总数。
- 上限为 `0` 时显示总数 `0`、剩余 `0`。
- 原有待转奖励和历史奖励额度保持不变。

## 后端结构

新增一个小的邀请限制规则层，避免把判断散落在注册控制器、OAuth 控制器和 UI 里。

建议函数：

- `registration_setting.GetSettings()` 返回必填邀请码设置和默认邀请限制设置。
- `model.CountSuccessfulInvites(inviterId int)` 统计成功邀请人数。
- `model.GetInviteLimitSubject(inviterId int)` 或类似函数返回邀请人的角色和用户级覆盖设置。
- 在 service 或 controller helper 中计算 `InviteLimitStatus`：
  - `unlimited`
  - `limit`
  - `used`
  - `remaining`
  - `exempt`
- 所有注册流在解析邀请码后、创建用户前，调用同一个 validator。

这样后期可以比较自然地扩展为按分组限制、按时间窗口限制、按套餐限制，或者为来源归因单独增加限制规则。

## 数据迁移

用 `AutoMigrate` 增加用户字段。默认值必须兼容老站点：

- 已有普通用户默认跟随系统设置。
- 系统默认“不限制”，避免升级后意外阻断现有注册流程。

新增字段需要同时兼容 SQLite 和 MySQL。

## 测试

后端测试：

- 系统为有限模式且上限为 `0` 时，普通用户的邀请码不能再成功邀请注册。
- 系统为正整数上限时，未达到上限允许注册，达到上限后阻止注册。
- 系统为“不限制”时，普通用户可以继续邀请注册。
- 用户级有限覆盖优先于系统不限制。
- 用户级不限制覆盖优先于系统有限。
- 管理员和超级管理员作为邀请人时绕过限制。
- 来源归因忽略邀请限制。
- 已删除的被邀请用户仍计入成功邀请人数。
- OAuth 注册使用同一套邀请限制校验。

前端检查：

- 默认前端构建和类型检查通过。
- 注册设置页可以展示和保存“不限制”与数字上限。
- 钱包能展示已邀请、上限和剩余名额。
- 成员编辑抽屉能提交用户级邀请限制覆盖。
- 操练场可以选择图片和文本文件、移除附件，并构建预期 payload。

运行时冒烟：

- 普通邀请人未达到上限时，注册成功。
- 同一普通邀请人达到上限时，注册失败且错误清晰。
- 管理员邀请码在普通限制下仍可注册成功。
- 来源归因目标用户达到邀请上限时，来源归因仍成功。
- 操练场能向 `/pg/chat/completions` 发送图片 payload。
